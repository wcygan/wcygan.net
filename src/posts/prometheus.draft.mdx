[Prometheus](https://github.com/prometheus/prometheus) collects operational
measurements over time. Request counts, error rates, latency, and resource usage
help explain whether a slow API is receiving more traffic, failing requests, or
accumulating work.

## Monitoring architecture

Prometheus collects metrics, stores their timestamped history in a **time-series
database**, and evaluates queries and alerting rules against that history. The
[architecture overview](https://prometheus.io/docs/introduction/overview/)
describes how these operations fit together.

An **instance** is one target that Prometheus collects metrics from. A **job**
groups targets, and an **exporter** exposes another system's metrics. These
measurements summarize operational behavior; they do not preserve every
transaction.

## Time-series identity

In the [Prometheus data model](https://prometheus.io/docs/concepts/data_model/),
a metric name and its complete label set identify one **time series**. A
**label** is a name/value pair, such as `route="/fast"` or `status="200"`. Each
series contains a sequence of timestamp/value samples. Changing a label creates
a different series.

```text
demo_http_requests_total{job="demo",instance="app:8080",route="/fast",status="200"}

12:00:00  42
12:00:05  49
12:00:10  58
```

Application code defines metric names, units, and labels without a
`CREATE TABLE` step. Prometheus adds `job` and `instance` to the measurements it
collects from a target. Its [naming conventions](https://prometheus.io/docs/practices/naming/)
help keep measurements consistent across the application.

## Label cardinality

**Cardinality** is the number of distinct time series. An additional label can
multiply the number of label combinations and therefore the number of series.
Prometheus stores only the combinations it observes.

More series require more memory and query work. Use route labels with a bounded
set of values, and keep user IDs in logs or traces. The
[label guidance](https://prometheus.io/docs/practices/instrumentation/#do-not-overuse-labels)
explains why unrestricted label values increase the cost of instrumentation.

## Counters, gauges, and histograms

Prometheus [metric types](https://prometheus.io/docs/concepts/metric_types/)
describe different kinds of measurement. A **counter** accumulates events until
its process resets. A **gauge** rises and falls, as the number of requests in
flight does. A **histogram** records a distribution of observations.

```python
from prometheus_client import Counter, Gauge, Histogram

REQUESTS = Counter("demo_http_requests_total", "Completed requests", ["route", "status"])
IN_FLIGHT = Gauge("demo_http_requests_in_flight", "Active requests", ["route"])
DURATION = Histogram("demo_http_request_duration_seconds", "Request duration", ["route"])

IN_FLIGHT.labels(route="/fast").inc()
IN_FLIGHT.labels(route="/fast").dec()
REQUESTS.labels(route="/fast", status="200").inc()
DURATION.labels(route="/fast").observe(0.02)
```

The [Python client instrumentation guide](https://prometheus.github.io/client_python/instrumenting/)
describes how to define and update these instruments.

## Metric collection and scraping

[Instrumented application code](https://prometheus.io/docs/tutorials/instrumenting_http_server_in_go/)
exposes measurements at `/metrics`. Prometheus periodically requests that
endpoint and stores the returned measurements. Each request is a **scrape**,
the ordinary path by which application measurements reach Prometheus.

```text
# TYPE demo_http_requests_total counter
demo_http_requests_total{route="/fast",status="200"} 42
demo_http_requests_total{route="/fail",status="500"} 3
```

Prometheus also records
[`up`](https://prometheus.io/docs/concepts/jobs_instances/#automatically-generated-labels-and-time-series):
`1` means the scrape succeeded, and `0` means it failed. A successful scrape
shows that Prometheus collected metrics; it does not prove that the application
can complete business requests.

## Local storage and retention

After a scrape, recent samples enter the **Head**, the storage area for current
data. A **write-ahead log** (WAL) supports crash recovery. Older samples become
persisted blocks, which compaction combines. The
[on-disk layout](https://prometheus.io/docs/prometheus/latest/storage/#on-disk-layout)
describes these storage structures.

Retention deletes expired blocks, while compaction preserves sample detail.
Each server's local storage is independent.
[Remote storage integrations](https://prometheus.io/docs/prometheus/latest/storage/#remote-storage-integrations)
provide a separate storage path.

## Counter rates in PromQL

**PromQL** is the query language for the collected time series. A range selector
such as `[1m]` selects a minute of samples. The `rate` function estimates counter
growth per second and handles observed counter resets. Apply `rate` **before**
summing the results. The
[query basics](https://prometheus.io/docs/prometheus/latest/querying/basics/)
cover selectors and expressions.

```text
# Read cumulative counts
demo_http_requests_total{job="demo",route="/fast"}

# Requests per second, grouped by route
sum by (route) (rate(demo_http_requests_total{job="demo"}[1m]))

# Fraction of requests returning server errors
sum(rate(demo_http_requests_total{job="demo",status=~"5.."}[1m]))
/
sum(rate(demo_http_requests_total{job="demo"}[1m]))
```

A rate calculation needs at least two samples. The
[`rate` function](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate)
extrapolates counter growth to the range boundaries. The error-ratio query is
undefined when there is no traffic.

## Classic histograms and latency percentiles

An average can hide slow requests. A
[**classic histogram**](https://prometheus.io/docs/practices/histograms/) counts
observations in cumulative buckets. Each bucket includes durations at or below
its `le` boundary, so the buckets overlap. The `+Inf` bucket includes every
observation.

Estimate the 90th percentile in seconds:

```text
histogram_quantile(0.9,
  sum by (le, route) (
    rate(demo_http_request_duration_seconds_bucket{job="demo"}[1m])
  )
)
```

Keep the `le` label when combining classic histogram buckets so that
[`histogram_quantile`](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile)
can identify their boundaries. Those boundaries affect the estimate's accuracy.
Combine the buckets to calculate a percentile across instances; do not average
per-instance percentiles.

## Recording rules

A [**recording rule**](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/)
runs a query on a schedule and saves its results as new time series. Dashboards
can read those series directly instead of repeating the aggregation.

```yaml
groups:
  - name: demo-rollups
    interval: 5s
    rules:
      - record: job_route:demo_http_requests:rate1m
        expr: sum by (job, route) (rate(demo_http_requests_total{job="demo"}[1m]))
```

Read the recorded aggregation with `job_route:demo_http_requests:rate1m`.
Recording rules add series without replacing raw samples or backfilling history.
They also do not make local storage automatically downsample older data; see the
[storage limitations](https://prometheus.io/docs/prometheus/latest/storage/).

## Alert evaluation and notifications

An [alerting rule](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)
evaluates a condition against the stored metrics. An alert becomes **pending**,
then **firing** if the condition persists for the configured duration. A false
evaluation resets that timer. Alertmanager routes the resulting notifications.

## Run Prometheus locally

Use Docker and Compose to run the site's `examples/prometheus/` lab. It pins
[Prometheus 3.15.0](https://github.com/prometheus/prometheus/releases/tag/v3.15.0)
and [Python client 0.26.0](https://github.com/prometheus/client_python/releases/tag/v0.26.0).
From the repository root:

```bash
cd examples/prometheus
docker compose up -d --build
docker compose exec -T app python traffic.py --seconds 90 --mode mixed
```

Open the application's [metrics endpoint](http://127.0.0.1:18080/metrics) and the
[Prometheus interface](http://127.0.0.1:19090). In Targets, check that `demo` is
healthy. Prometheus scrapes this target every five seconds.

Run the queries above to compare `/fast` and `/slow` latency and inspect errors
from `/fail`. Open Alerts to inspect alert state. To evaluate a query through
the HTTP API, run:

```bash
curl --get 'http://127.0.0.1:19090/api/v1/query' \
  --data-urlencode 'query=sum(rate(demo_http_requests_total{job="demo"}[1m]))'
```

The [query API](https://prometheus.io/docs/prometheus/latest/querying/api/)
returns the expression's result. Use these three experiments to compare the
measurements with application behavior:

1. `docker compose restart app`: observe counter resets and their rates.
2. `docker compose stop app`: observe `up = 0`, then run `docker compose start app`.
3. Read `job_route:demo_http_requests:rate1m` and compare the raw rate query.

The lab exposes alert state without sending notifications. Its README includes
rule tests, configuration checks, and additional experiments. Stop the lab when
finished:

```bash
docker compose down
```

## Explain Prometheus in an interview

Describe the four operations: instrument application code, scrape measurements,
query time series, and evaluate alerts. Explain how label cardinality increases
resource costs and why sampled metrics do not form an exact event ledger.
