An index is an ordered structure that helps a database locate data. It trades storage space and write maintenance for less searching. These small demos show the basic mechanics; the page sizes, tree depth, and work counts are illustrative.

## Finding a record

A table can contain millions of records. Without a useful index for your filter, the engine may inspect every record to find the matches. Our example searches a name in records ordered by ID.

## Following a sorted tree

An index keeps keys in order. A B+ tree uses separator keys to route searches into smaller groups. It remains shallow because each page can have many children.

Knowing the new record’s key is enough to locate its destination leaf. This is why an insert does not need the name scan shown earlier.

## Making room for new entries

Pages have finite space. Splits keep the tree usable as data grows, but they add work to a write. The capacity of three keys here is only for teaching.

## Searching a different column

InnoDB stores full records in its primary-key tree. A secondary index on name gives a name search its own sorted path. Its entries contain the primary key, which leads to the full record.

<IndexingPrimerDemo lesson="secondary" />

## Finding several neighboring keys

An ordered index is useful for more than equality. After seeking a starting key, a range search can follow the linked leaves until it reaches the end of the range.

<IndexingPrimerDemo lesson="range" />

## Choosing the order of columns

A compound index sorts by its first column, then its second. Its leading columns determine which filters naturally form a searchable continuous range. Engines may have additional strategies such as skip scans; this shows the basic ordering.

<IndexingPrimerDemo lesson="compound" />

## Answering from the index

A covering index contains every field needed by a query. It can avoid the usual second lookup for the table record. Adding fields also increases index size and write maintenance.

<IndexingPrimerDemo lesson="cover" />

## Skipping enough work to matter

Selectivity describes how narrow a filter is. An index is not automatically the cheapest plan. Fetching many scattered full records can cost more than scanning the table; caching, row size, and the requested fields all matter.

## Paying for indexes on writes

Each index occupies space and must stay consistent with the table. Inserts add entries, deletes remove them, and updates maintain affected entries. The counts below describe structures maintained, not physical disk writes.

## Keeping references stable

InnoDB secondary entries use primary keys instead of physical record addresses. Keeping that key unchanged allows a reference to survive changes in storage placement. Here, a full row grows because an unindexed field changes. The primary leaf splits, but the name entry still stores the same ID. The split and tiny page capacities are illustrative.

<IndexingPrimerDemo lesson="stable" />

## What to remember

Choose indexes around the filters, joins, and ordering your queries actually use. An index is useful when it avoids enough work to pay for its storage and maintenance. Use your database’s query plan to check whether it is used and how many records the query reads.

The primary and secondary layouts here describe MySQL’s InnoDB engine. Other engines organize records differently. PostgreSQL usually keeps rows in a separate heap; its update and index-maintenance behavior also depends on row versions and HOT updates.
