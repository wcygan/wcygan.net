Consensus algorithms let multiple processes in a distributed system agree on a value. They aim to provide three properties:

- **Agreement**, meaning all correct processes decide on the same value.
- **Validity**, meaning that value was proposed by one of the processes.
- **Termination**, meaning all correct processes eventually reach a decision.

A correct process is one that follows the algorithm and does not fail; termination depends on the algorithm’s assumptions about failures and communication.

## Why Ordering Matters

Applying the same operations in a different order can produce a different result.

<OperationOrderFigure />

## Total Order Broadcast

[Total order broadcast](https://en.wikipedia.org/wiki/Atomic_broadcast), also called atomic broadcast, ensures every participating correct process delivers the same messages in the same order. Replicas can deliver messages at different times, but their delivered sequences agree wherever they overlap. Reliable delivery matters as well as ordering.

<TotalOrderBroadcastFigure />

Atomic broadcast and consensus are [equivalent under matching assumptions about the system and failures](https://cs.nyu.edu/~apanda/classes/sp26/papers/chandra-toueg.pdf). To reach consensus, processes can broadcast proposals and decide on the first delivered value. In the other direction, repeated consensus decisions can choose successive batches of messages for ordered delivery.

## Raft: Understandable Consensus

[Raft](https://raft.github.io/) is a consensus algorithm designed to be easy to understand. Its elected leader orders new log entries and coordinates copying them across servers, so the servers apply committed operations in the same order. The [Raft paper, _In Search of an Understandable Consensus Algorithm_](https://raft.github.io/raft.pdf), explains how this works.

Each server runs a **state machine**: it applies commands from the log to its local state. Servers that start with the same state reach the same result when they apply the same deterministic commands in the same order. A deterministic command always produces the same result from the same input.

Raft assumes servers follow the protocol, even though they can crash and restart. Logs, term numbers, and votes must survive a restart. Delays can stop progress, but must never undo a committed decision. Making progress requires a communicating majority and enough time to elect and keep a leader.

### Roles and Terms

Each server has one of three roles:

- **Follower:** responds to the leader and votes in elections.
- **Candidate:** asks for votes to become leader.
- **Leader:** orders new log entries and sends them to followers.

A **term** is a numbered period that starts with an election and continues through the elected leader’s tenure. It has at most one leader; an election can also finish without choosing one. Servers learn about newer terms through messages, so they can temporarily disagree about the current term.

<RaftRoleTransitionsFigure />

### Leader Election

Followers expect regular heartbeats from the leader. When a follower waits too long without receiving one, it becomes a candidate and asks the other servers for votes. In this three-server example, it needs two votes to become leader.

Each server can vote for only one candidate per term. Followers wait for different, randomly chosen amounts of time before starting an election, reducing the chance that several candidates start together. If the vote splits, they try again in a new term.

### Log Replication

<span id="committing-and-applying-entries" />

The leader gives each new command a position in its log, then sends copies to the followers. Each entry records the command and the term in which the leader accepted it. Followers store the entries in the same order and confirm when they have been saved durably.

An entry passes through several steps:

- Once a majority has stored an entry from the leader’s current term, the leader can commit it.
- The leader tells followers how far the log is committed, through replication messages and heartbeats.
- Each server applies the commands it knows are committed, in log order.

The commit index is the highest entry a server knows is committed. Last applied is the highest entry it has executed. A server can know an entry is committed before it has applied it.

This example uses three servers, so two stored copies form a majority. Each server’s **Stored** and **Commit** labels show its own progress. A message’s **Commit** field carries the leader’s known commit index.

<RaftLogReplicationFigure />

A lagging follower can receive several missing entries together and catch up.

### Leader Failure and Recovery

A missed heartbeat does not prove that the leader crashed: a slow network can look the same. If the leader is lost, new writes wait until a suitable candidate wins a majority. An isolated follower timing out does not by itself stop a healthy majority from accepting writes.

A server rejects vote requests from older terms. For a request in its current or a newer term, it also checks:

- The server has not voted for another candidate in that term.
- The candidate’s log is at least as up to date as the server’s own log.

[Raft compares the last entry’s term first](https://raft.github.io/raft.pdf#page=8). If the terms match, it compares the entry’s index. Starting a newer election does not make an outdated log eligible.

The next example starts at a later point in the same log. B leads in term 5. B and A know entry #4 is committed, while C still ends at #3.

<RaftLeaderRecoveryFigure />

The servers electing a new leader overlap with the servers that stored a committed entry. Together with the voting checks, this ensures that later leaders preserve committed entries.

A restarted server returns as a follower and catches up from the new leader. Without a reachable majority, new entries cannot commit. A returning server may also have uncommitted entries that disagree with the new leader.

### Why the Current Term Matters

The commitment rule specifically counts copies of an entry from the leader’s **current term**. An inherited entry keeps its original term, even when a newer leader copies it to more servers.

The next demo follows stages (a)–(e) of [Figure 8 in the Raft paper](https://raft.github.io/raft.pdf#page=8), adapted to three servers. Its boxes show entry terms, and its columns show log indexes. In (c), the term-2 entry reaches two servers, while the leader’s term-4 entry remains local. The older entry still cannot be declared committed by counting copies.

Stages (d) and (e) are alternative endings from (c): crashing first allows both uncommitted entries to be overwritten; replicating the term-4 entry to a majority commits it and the preceding log. With three servers, stage (a) starts with just one copy, because a second copy in term 2 would already commit that entry.

### Repairing Conflicting Logs

A leader can accept an entry and fail before a majority stores it. A later leader may accept a different command at the same position.

Each replication request includes the index and term of the entry immediately before the new entries. The follower checks that entry against its own log. If they disagree, it rejects the request without changing its log.

The leader moves `nextIndex`, the next position it will send to that follower, backward and retries until it finds a matching entry.

<RaftLogConflictFigure />

Once that entry matches, the follower:

1. Compares the incoming entries with its own.
2. At the first conflicting term, deletes that entry and every entry after it.
3. Stores the leader’s replacement entries durably.
4. Updates its commit index using the leader’s information, then acknowledges the request.

A matching preceding entry alone does not cause deletion. An incoming entry must conflict with an existing one.

Only uncommitted entries can be replaced. The [Raft paper](https://raft.github.io/raft.pdf#page=4) describes these checks.

## Conclusion

Raft gives servers a shared order for commands and preserves committed entries when leaders change. A majority lets the cluster make progress while slower servers catch up. If too few servers can communicate, new entries wait until a majority is reachable again.
