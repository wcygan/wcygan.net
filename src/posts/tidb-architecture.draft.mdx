**TiDB is a distributed SQL database.** Applications use SQL while TiDB distributes query execution and data storage across machines. In [TiDB Self-Managed](https://docs.pingcap.com/tidb/stable/tidb-architecture/), separate components handle SQL execution, transactional storage, cluster coordination, and columnar analytics.

## Single-machine resource limits

As data and query volume grow, SQL execution and storage compete for one host's resources. TiDB separates SQL compute from storage so these layers can grow independently.

## SQL, storage, and coordination

TiDB plans SQL queries, TiKV stores rows, and **PD**, the Placement Driver, coordinates placement and timestamps. The optional TiFlash component keeps a column-oriented copy of the data for analytics.

TiDB supports the MySQL protocol, but protocol compatibility does not guarantee application compatibility. Check [compatibility](https://docs.pingcap.com/tidb/stable/mysql-compatibility/) before migrating: stored procedures and triggers are unsupported.

## Region key ranges

A **Region** is a contiguous range of keys. Splitting a Region produces smaller key ranges that the cluster can place independently.

## Point-read routing

A **point read** retrieves a row by key. For example, an application can request an order by its primary key. It sends SQL to TiDB, which identifies the Region containing the requested key and retrieves the row from TiKV.

## Secondary index lookups

A query that searches orders by buyer and returns an amount can require two lookups. A secondary index on buyer returns a row ID; TiDB then uses that ID to retrieve the amount from the row. A covering index can avoid the second lookup by including the requested data.

## Raft replication and quorum

Each Region has replicas that hold copies of its key range. **Raft** keeps those replicas in agreement about changes. A new entry requires acknowledgment from a majority of voting replicas, called a **quorum**. In a group of three voting replicas, two must acknowledge the entry. If two are unavailable, the remaining replica cannot form a quorum.

Replicas need separate failure domains. Three processes on one laptop still fail together if that laptop fails.

## Cross-Region transactions

A transaction groups updates into one commit or abort outcome. An order and its inventory update can touch different Regions, so a transaction protocol coordinates their outcome across those Regions. This all-or-nothing property is **atomicity**. Raft replication within each Region and transaction coordination across Regions solve different problems: keeping replicas in agreement and preserving the transaction's atomicity.

## Snapshot isolation

Transactions produce committed versions of the data. A read timestamp determines which of those versions a query can see. A version committed after that timestamp is outside the query's snapshot.

[Snapshot isolation](https://docs.pingcap.com/tidb/stable/transaction-isolation-levels/) can allow write skew. A consistent snapshot does not guarantee serializable transactions.

## TiFlash columnar replicas

Point lookups and large aggregations benefit from different data layouts. TiFlash adds columnar replicas for analytical queries over transactional data, an approach called **hybrid transactional and analytical processing (HTAP)**.

TiFlash replicas are enabled per table. For [consistent reads](https://docs.pingcap.com/tidb/stable/tiflash-overview/), TiFlash validates replication progress and may wait for its replicas to catch up.

## Independent compute and storage scaling

TiDB servers add SQL execution capacity; TiKV stores add data capacity. The cluster moves Region replicas as it rebalances.

| Consider TiDB when…                             | Remember…                              |
| ----------------------------------------------- | -------------------------------------- |
| Transactional data or traffic outgrows one host | Network coordination adds cost         |
| Analytics needs recent application data         | Test TiFlash on representative queries |
| Compute and storage grow at different rates     | Hot keys can remain bottlenecks        |

A single-machine MySQL or PostgreSQL database may be simpler to operate when it comfortably serves the workload.

## Run a local TiDB cluster

[TiUP Playground](https://docs.pingcap.com/tidb/stable/quick-start-with-tidb/) runs a learning cluster on macOS or Linux. Install a MySQL client before starting the cluster. The commands below follow the documentation and pin TiDB to v8.5.8; I haven't run this lab yet.

```sh
curl --proto '=https' --tlsv1.2 -sSf \
  https://tiup-mirrors.pingcap.com/install.sh | sh

# Open a new terminal, then keep this running:
tiup playground v8.5.8 --db 1 --pd 1 --kv 1 --tiflash 1
```

Check the [TiFlash requirements](https://docs.pingcap.com/tidb/stable/hardware-and-software-requirements/) before starting Playground. Use `--tiflash 0` if your machine does not support TiFlash. This single-machine setup cannot demonstrate replica failover.

In another terminal, connect with the MySQL client. Use the address printed by Playground, normally:

```sh
mysql --comments --host 127.0.0.1 --port 4000 -u root
```

Create four orders, update one inside a transaction, and query the result:

```sql
CREATE DATABASE tidb_learning;
USE tidb_learning;
CREATE TABLE orders (
  id BIGINT PRIMARY KEY CLUSTERED,
  buyer VARCHAR(32),
  amount INT,
  INDEX buyer_idx (buyer)
);
INSERT INTO orders VALUES
  (1, 'Ada', 12), (2, 'Lin', 9),
  (3, 'Sam', 18), (4, 'Jo', 5);

BEGIN;
UPDATE orders SET buyer = 'Will' WHERE id = 2;
COMMIT;

SELECT * FROM orders WHERE id = 2; -- Will, amount 9
SELECT SUM(amount) FROM orders;   -- 44
EXPLAIN SELECT * FROM orders WHERE buyer = 'Will';
```

To compare row and columnar query execution, [enable a TiFlash replica](https://docs.pingcap.com/tidb/stable/create-tiflash-replicas/) and wait until `AVAILABLE = 1`. Then compare the aggregation's execution plans. Four rows illustrate query behavior; performance testing requires a realistic dataset.

Press **Ctrl+C** in the Playground terminal to stop the cluster. Untagged data is disposable. To retain data between runs, [use a tag](https://docs.pingcap.com/tidb/stable/tiup-playground/).
