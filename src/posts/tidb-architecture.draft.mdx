**TiDB is a distributed SQL database:** one familiar SQL interface, with data and work spread across machines. These ten demos explore [TiDB Self-Managed](https://docs.pingcap.com/tidb/stable/tidb-architecture/), starting with the problem it solves.

Demos play as you scroll. **Pause** to inspect; drag 3D scenes to look around.

## Outgrowing one machine

More data and queries eventually compete for one host's resources. TiDB separates SQL compute from storage.

<TidbLearningDemo lesson="capacity" />

## Meet the components

TiDB plans SQL. TiKV stores rows. **PD**, the Placement Driver, coordinates placement and timestamps. Optional TiFlash stores columns.

<TidbLearningDemo lesson="roles" />

TiDB speaks the MySQL protocol. Check [compatibility](https://docs.pingcap.com/tidb/stable/mysql-compatibility/) before migrating; stored procedures and triggers are unsupported.

## Split the data

A **Region** is a contiguous range of keys. Splitting creates smaller ranges that can be placed independently.

<TidbLearningDemo lesson="regions" />

## Follow a read

The application sends SQL. TiDB locates the right Region and requests a row from TiKV.

<TidbLearningDemo lesson="routing" />

## Keep copies

Each Region uses **Raft**, a protocol for agreeing on changes. With three voting replicas, two must acknowledge a new entry.

<TidbLearningDemo lesson="quorum" />

Try losing one follower, then two. Copies need separate failure domains: three processes on one laptop still fail together.

## Commit across Regions

An order and its inventory update can touch different Regions. A transaction protocol connects their outcomes.

<TidbLearningDemo lesson="transaction" />

## Look up an index

The email index finds a row ID. A second lookup retrieves the requested name. A covering index can avoid that second lookup.

<TidbLearningDemo lesson="index" />

## Read a consistent snapshot

A read timestamp fixes which committed versions are visible. Try snapshots **80**, **120**, and **160**.

<TidbLearningDemo lesson="snapshot" />

[Snapshot isolation](https://docs.pingcap.com/tidb/stable/transaction-isolation-levels/) can allow write skew; it does not guarantee serializable transactions.

## Analyze columns

Point lookups and large aggregations need different layouts. TiFlash adds columnar replicas for analytical queries over transactional data: **hybrid transactional and analytical processing (HTAP)**.

<TidbLearningDemo lesson="tiflash" />

TiFlash replicas are enabled per table. [Consistent reads](https://docs.pingcap.com/tidb/stable/tiflash-overview/) validate replication progress and may wait for catch-up.

## Grow each layer

Add TiDB servers for SQL execution, or TiKV stores for data capacity. Region replicas move as the cluster rebalances.

<TidbLearningDemo lesson="scaling" />

| Consider TiDB when…                             | Remember…                              |
| ----------------------------------------------- | -------------------------------------- |
| Transactional data or traffic outgrows one host | Network coordination adds cost         |
| Analytics needs recent application data         | Test TiFlash on representative queries |
| Compute and storage grow at different rates     | Hot keys can remain bottlenecks        |

If one MySQL or PostgreSQL machine comfortably serves the workload, its simpler operation may be enough.

## Try it locally

[TiUP Playground](https://docs.pingcap.com/tidb/stable/quick-start-with-tidb/) runs a learning cluster on macOS or Linux. Install a MySQL client first. These v8.5.8 commands follow the documentation; I haven't run this lab yet.

```sh
curl --proto '=https' --tlsv1.2 -sSf \
  https://tiup-mirrors.pingcap.com/install.sh | sh

# Open a new terminal, then keep this running:
tiup playground v8.5.8 --db 1 --pd 1 --kv 1 --tiflash 1
```

Check the [TiFlash requirements](https://docs.pingcap.com/tidb/stable/hardware-and-software-requirements/); use `--tiflash 0` if unsupported. This single-machine setup cannot demonstrate replica failover.

In another terminal, connect to the address printed by Playground, normally:

```sh
mysql --comments --host 127.0.0.1 --port 4000 -u root
```

Run a tiny transaction and aggregation:

```sql
CREATE DATABASE tidb_learning;
USE tidb_learning;
CREATE TABLE orders (
  id BIGINT PRIMARY KEY CLUSTERED,
  buyer VARCHAR(32),
  amount INT,
  INDEX buyer_idx (buyer)
);
INSERT INTO orders VALUES
  (1, 'Ada', 12), (2, 'Lin', 9),
  (3, 'Sam', 18), (4, 'Jo', 5);

BEGIN;
UPDATE orders SET buyer = 'Will' WHERE id = 2;
COMMIT;

SELECT * FROM orders WHERE id = 2; -- Will, amount 9
SELECT SUM(amount) FROM orders;   -- 44
EXPLAIN SELECT * FROM orders WHERE buyer = 'Will';
```

Next, [enable a TiFlash replica](https://docs.pingcap.com/tidb/stable/create-tiflash-replicas/), wait until `AVAILABLE = 1`, and compare the aggregation's execution plans. Four rows teach query behavior; performance testing needs a realistic dataset.

Press **Ctrl+C** in the Playground terminal to stop. Untagged data is disposable; [use a tag](https://docs.pingcap.com/tidb/stable/tiup-playground/) to keep it between runs.

For deeper detail: PingCAP's [architecture](https://docs.pingcap.com/tidb/stable/tidb-architecture/), [storage](https://docs.pingcap.com/tidb/stable/tidb-storage/), and [transaction](https://docs.pingcap.com/tidb/stable/tidb-faq/#does-tidb-support-distributed-transactions) guides. Demo counts, boundaries, and timing are illustrative.
