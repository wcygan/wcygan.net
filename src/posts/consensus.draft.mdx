Consensus algorithms let multiple processes in a distributed system agree on a value. They aim to provide three properties:

- **Agreement**, meaning all correct processes decide on the same value.
- **Validity**, meaning that value was proposed by one of the processes.
- **Termination**, meaning all correct processes eventually reach a decision.

A correct process is one that follows the algorithm and does not fail; termination depends on the algorithm’s assumptions about failures and communication.

## Why Ordering Matters

Applying the same operations in a different order can produce a different result.

<OperationOrderFigure />

## Total Order Broadcast

[Total order broadcast](https://en.wikipedia.org/wiki/Atomic_broadcast) ensures every participating correct process delivers the same messages in the same order, so each replica applies the operations consistently. This reliable form, also called atomic broadcast, is [equivalent to consensus under matching assumptions about the system and failures](https://cs.nyu.edu/~apanda/classes/sp26/papers/chandra-toueg.pdf): processes can broadcast proposals and decide on the first value delivered, while repeated consensus decisions can select the next batch of messages for ordered delivery. Ordering alone, without reliable delivery, is not enough.

## Raft: Understandable Consensus

[Raft](https://raft.github.io/) is a consensus algorithm designed to be easy to understand. Its elected leader orders new log entries and coordinates copying them across servers, so the servers apply committed operations in the same order. The [Raft paper, _In Search of an Understandable Consensus Algorithm_](https://raft.github.io/raft.pdf), explains how this works.

### Roles and Terms

Each server has one of three roles:

- **Follower:** responds to the leader and votes in elections.
- **Candidate:** asks for votes to become leader.
- **Leader:** orders new log entries and sends them to followers.

A **term** is a numbered election round. Each term starts with an election and has at most one leader. An election can finish without choosing a leader.

<RaftRoleTransitionsFigure />

### Leader Election

Followers expect regular heartbeats from the leader. If those messages stop arriving, a follower eventually starts an election. It asks the other servers for their votes; in a five-server cluster, three votes are enough to become leader.

Each server votes for at most one candidate per term. Followers use randomized election timeouts to reduce the chance of starting competing elections together. If the vote splits, they try again in a new term.

<RaftLeaderElectionFigure />

A majority elects the leader. Randomized timing helps the cluster reach that majority.

Any two majorities must share at least one server. That shared server cannot vote for two candidates in the same term, so both candidates cannot win in that term.

<RaftMajorityOverlapFigure />

Once elected, the leader coordinates the order of new log entries.

### Log Replication

The leader gives each new command a position in its log, then sends copies to the followers. Each entry records the command and the term in which the leader accepted it. Followers store the entries in the same order and confirm when they have been saved.

<RaftLogReplicationFigure />

The leader can commit a new entry once a majority has stored it, without waiting for every follower. A lagging follower can catch up by receiving several missing entries together.

Storing an entry and knowing it is committed are separate steps. The leader includes its commit index in messages that copy entries and in heartbeats; followers update their own commit index when they receive that information.
