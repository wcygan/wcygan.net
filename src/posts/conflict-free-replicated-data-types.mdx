[Conflict-free replicated data types (CRDTs)](https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type) let copies of shared data accept updates independently. Once every copy receives the same updates, they agree.

A grow-only counter, or [G-Counter](<https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type#G-Counter_(Grow-only_Counter)>), is a simple example. Each node stores a list of counts, called a vector, with one position per node: <span className="gc-vector">[<NodeLetter index={0} />, <NodeLetter index={1} />, <NodeLetter index={2} />]</span>. A node increments only its own position. Add the entries to read the total.

Nodes share copies of their vectors. When a copy arrives, the receiver keeps the larger number in each position.

Because each position only grows, a G-Counter cannot decrement or remove an increment. Those operations need a different CRDT design, such as a PN-Counter.

## How the merge operation works

A and C each increment once, producing <VectorNotation value={[1, 0, 0]} /> and <VectorNotation value={[0, 0, 1]} />. The merge keeps the larger number in each position, so their combined state is <VectorNotation value={[1, 0, 1]} />.

<GrowOnlyCounterMergeEquation />

Messages carry saved counts; sending or receiving them does not add increments. Each message keeps the state it had when sent.

After A and C exchange their saved counts, both read `1 + 0 + 1 = 2`. We merge their vectors; we do not add the totals from the two copies.

## Why delivery order does not matter

Each merge keeps the larger count in every position.

<GrowOnlyCounterDeliveryOrderEquation />

Duplicates do not change the result: merging <VectorNotation value={[1, 0, 1]} /> with <VectorNotation value={[1, 0, 0]} /> still gives <VectorNotation value={[1, 0, 1]} />.

Delayed messages can leave replicas out of sync. Once each receives both increments, they agree. No coordination is needed: nodes update only their own position, and merging never lowers a count.

## The connection to vector clocks

Imagine a social media application where users can like posts. Each Like button click increments the post's counter, so A and C can each accept a like before hearing from the other. These events are **concurrent**: neither could have influenced the other, regardless of wall-clock time.

When C receives A’s count, it shows 2 likes. A’s like now influences C’s total—a **causal relationship**.

<CausalRelationshipDemo />

**A1** is the first like accepted by A. **C1** is the concurrent like accepted by C. Neither server has heard about the other yet, so neither event caused the other. **C2** is the later event at C after C receives A's saved state. C2 could not possibly show two likes without receiving A1's state: before that message, C knew only about C1 and could show only one like. That dependency—A1 must happen before C2 in the information flow—is the causal relationship.

[Vector clocks](https://en.wikipedia.org/wiki/Vector_clock) track whether events could have influenced each other or were concurrent, without synchronized clocks. G-Counters borrow their vector and maximum-merge approach, but count application increments, not message sends or receives.
