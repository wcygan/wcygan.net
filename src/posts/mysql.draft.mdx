[MySQL](https://dev.mysql.com/doc/refman/8.4/en/what-is-mysql.html) is a relational database server.
It stores related records in tables and uses SQL to read and change them. The examples
use a bookstore database in MySQL 8.4 to explain queries, transactions, storage, and replication.

## Tables, keys, and joins

A table stores records as rows. A primary key identifies a row within that table.
In the bookstore, a
[foreign key](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)
connects each order to a customer. A `JOIN` matches rows from the two tables so a
query can return an order alongside its customer's information.

## Constraints

The schema defines the tables and declares rules that MySQL checks when data changes.
Primary keys reject
duplicate IDs, foreign keys reject orders that reference missing customers, and
[CHECK constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)
reject negative stock.

## Filtering and aggregation

A query can use `WHERE` to select Ada's orders and `SUM` to add their amounts.
Her two orders are 2,900 cents and 4,500 cents, producing a total of 7,400 cents.

## Query processing

The application sends a SQL statement to MySQL to request a read or a change.
MySQL plans how to carry out the query, and
[InnoDB](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html), the storage engine,
accesses the rows the operation needs.

## Index lookups and covering queries

An [index](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) locates entries
that match a query. When the index contains every value the query needs, a covering
query can return the answer without fetching the full rows.

## Buffer pool

InnoDB stores table and index data in blocks called pages. It keeps pages in memory
in the [buffer pool](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html),
so a read can reuse a page already loaded instead of reading it from disk again.

## Transactions

A checkout creates an order and reduces the remaining stock. A
[transaction](https://dev.mysql.com/doc/refman/8.4/en/mysql-acid.html) groups those changes
so the application can commit both or roll both back. Committing retains the changes;
rolling back undoes the pending changes.

## Row locks

Consider two shoppers trying to buy the last copy of a book. The first shopper runs a
[locking read](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)
inside a transaction, holding the inventory row while the checkout proceeds.
The second shopper's locking read waits; after the first sale commits, it sees zero stock.

## Redo and crash recovery

Durability means that a committed change survives a crash. InnoDB can make a change
durable before its modified data page reaches disk. After a
[crash](https://dev.mysql.com/doc/refman/8.4/en/innodb-recovery.html), it uses redo,
a log of data modifications, to reconstruct the committed change if that page had
not yet been flushed. This requires the redo to be durable.

## Asynchronous replication

A replica is another server that receives changes from the source server. With
[asynchronous replication](https://dev.mysql.com/doc/refman/8.4/en/replication.html),
the replica can temporarily lack an order that has committed on the source. It must
apply the change before its reads include it; receiving the change alone is not enough.

## Relational workloads

Tables, relationships, and transactions support several kinds of application data:

- **Stores:** keep orders and inventory consistent
- **Accounts:** connect users, organizations, and memberships
- **Bookings:** coordinate competing reservations

## Run the bookstore locally

**Create the bookstore**

With Docker running, save the Compose configuration below as `compose.yaml` in a new
directory, then save the schema beside it. The
[official image](https://hub.docker.com/_/mysql) initializes a fresh database, and
the named volume retains its data between runs.

```yaml
name: mysql-primer-lab

services:
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: root-local-only
      MYSQL_DATABASE: bookstore
      MYSQL_USER: practice
      MYSQL_PASSWORD: practice-local-only
    ports:
      - 127.0.0.1:3307:3306
    volumes:
      - mysql-data:/var/lib/mysql
      - ./schema.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro
    healthcheck:
      test:
        - CMD-SHELL
        - >-
          MYSQL_PWD="$${MYSQL_PASSWORD}"
          mysql --protocol=TCP -h127.0.0.1 -u"$${MYSQL_USER}"
          "$${MYSQL_DATABASE}" -e 'SELECT 1 FROM orders LIMIT 1'
          >/dev/null 2>&1
      interval: 2s
      timeout: 5s
      retries: 60
      start_period: 20s

volumes:
  mysql-data:
```

Save the following SQL as `schema.sql`. Prices use integer cents, and `stock`
records the remaining inventory.

```sql
USE bookstore;

CREATE TABLE customers (
  id INT PRIMARY KEY,
  name VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE inventory (
  id INT PRIMARY KEY,
  title VARCHAR(200) NOT NULL,
  stock INT NOT NULL CHECK (stock >= 0),
  unit_price_cents INT NOT NULL CHECK (unit_price_cents > 0)
) ENGINE=InnoDB;

CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT NOT NULL,
  book_id INT NOT NULL,
  quantity INT NOT NULL CHECK (quantity > 0),
  total_cents INT NOT NULL CHECK (total_cents > 0),
  INDEX orders_customer_id (customer_id),
  INDEX orders_book_id (book_id),
  FOREIGN KEY (customer_id) REFERENCES customers(id),
  FOREIGN KEY (book_id) REFERENCES inventory(id)
) ENGINE=InnoDB;

INSERT INTO customers VALUES (1, 'Ada'), (2, 'Lin');
INSERT INTO inventory VALUES
  (1, 'SQL Basics', 2, 2900),
  (2, 'Reliable Systems', 5, 4500);
INSERT INTO orders VALUES
  (101, 1, 1, 1, 2900),
  (102, 1, 2, 1, 4500),
  (103, 2, 1, 1, 2900);
```

Start MySQL and open its client:

```sh
docker compose up -d --wait --wait-timeout 180
docker compose exec mysql mysql -upractice -p bookstore
```

Enter `practice-local-only` when prompted for the password. A desktop SQL client can
connect to `127.0.0.1:3307` using database `bookstore` and user `practice`.
These credentials are for the local exercise. If port `3307` is occupied, change
the host port in the Compose configuration.

**Read related records**

At the `mysql>` prompt, paste these statements without the prompt itself:

```sql
SELECT VERSION();

SELECT o.id, c.name, i.title, o.total_cents
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
JOIN inventory AS i ON i.id = o.book_id
ORDER BY o.id;

SELECT c.name, SUM(o.total_cents) AS spent_cents
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

The first join returns:

| id  | name | title            | total_cents |
| --- | ---- | ---------------- | ----------- |
| 101 | Ada  | SQL Basics       | 2900        |
| 102 | Ada  | Reliable Systems | 4500        |
| 103 | Lin  | SQL Basics       | 2900        |

The aggregate query returns 7,400 cents for Ada and 2,900 cents for Lin.

```sql
SHOW INDEX FROM orders;
EXPLAIN SELECT * FROM orders WHERE customer_id = 1;
```

[`EXPLAIN`](https://dev.mysql.com/doc/refman/8.4/en/explain.html) reports estimates
for the query plan rather than execution timings. With only three rows, MySQL may
choose a table scan even though an index exists.

**Roll back a checkout, then commit one**

Start a transaction and lock the inventory row. Keep every statement in the same
connection:

```sql
START TRANSACTION;
SELECT stock, unit_price_cents
FROM inventory WHERE id = 1 FOR UPDATE;

UPDATE inventory SET stock = stock - 1
WHERE id = 1 AND stock > 0;
SELECT ROW_COUNT() AS reserved;
```

With the seed data, stock starts at 2 and `reserved` is 1. **Continue only when
`reserved` is 1.** If it is 0, run `ROLLBACK;` and stop because the update did not
reserve a copy. An application must check this result and roll back on an error
before proceeding. A statement error does not always roll back the entire
transaction automatically; see
[InnoDB error handling](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html).

```sql
INSERT INTO orders (id, customer_id, book_id, quantity, total_cents)
VALUES (104, 2, 1, 1, 2900);

SELECT stock FROM inventory WHERE id = 1;
SELECT COUNT(*) AS order_count FROM orders;
ROLLBACK;

SELECT stock FROM inventory WHERE id = 1;
SELECT COUNT(*) AS order_count FROM orders;
```

Before rollback, the transaction sees stock 1 and four orders. After rollback,
stock returns to 2 and the order count returns to three. Repeat the checkout,
including the row-count check, and replace `ROLLBACK` with `COMMIT` to retain the
changes. Stock then stays at 1 and the order count stays at four. This exercise
uses the manual order ID 104; inserting it again after committing produces a
duplicate-key error.

**Keep or clear the data**

Exit the client with `exit`, then stop the server:

```sh
docker compose down
```

Restart the server with the earlier `up` command. The committed checkout remains
because `docker compose down` retains the volume. Initialization variables and
`schema.sql` apply only to a fresh data directory; editing the schema file does
not change an existing database.

To stop the lab and erase its saved data:

```sh
docker compose down -v
```

After the volume is erased, the next start initializes the seed data again.
To observe lock contention, run the same `FOR UPDATE` statement in two clients.
The second waits until the first commits or rolls back.
