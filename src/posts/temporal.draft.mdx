An order may require inventory reservation, payment, and fulfillment across
several services. A payment provider can time out, a worker can restart, and
fulfillment can become unavailable after the customer has paid. The application
needs to preserve completed work and identify the next operation after the
process coordinating the order stops.

[Temporal](https://temporal.io/) provides **durable execution** for application
processes whose progress must survive failures. You define the process in code.
Temporal records the information needed to reconstruct its state and continue
when the required infrastructure becomes available. The
[platform overview](https://docs.temporal.io/temporal) describes how the Temporal
Service and your application share that responsibility.

This introduction covers Temporal's programming model, recovery mechanisms,
and deployment responsibilities, followed by a local recovery experiment. My
earlier post on [durable execution](/durable-execution) explains the underlying
recovery mechanism.

## Durable execution and process recovery

A coordinator that stores order progress only in local variables loses that
progress when its process crashes. If inventory was reserved before the crash,
the reservation may still exist in the inventory service. A replacement process
cannot determine the next operation from the lost variables alone.

In the durable path, the system records an acknowledged result outside the
coordinator process. A replacement process can recover that progress and
continue. Applications can implement this persistence and recovery themselves;
Temporal supplies a platform and programming model for it. The application
still needs rules for permanent failures and external operations whose outcomes
are uncertain.

## Workflow Definitions and Activities

A [**Workflow Definition**](https://docs.temporal.io/workflows) describes how
operations are coordinated: reserve inventory, charge the customer, provision
the order, and send confirmation. A **Workflow Execution** is one instance of
that definition, such as the process for order `order-001`. Each execution has
its own input, state, and history.

An [**Activity**](https://docs.temporal.io/activity-definition) performs an
external operation, such as calling a payment API, writing to a database,
sending an email, or invoking a model. Workflow code chooses which Activities
to run and handles their results; Activity code performs the operations. An
Activity can contain several implementation steps, but those steps do not
automatically form a database transaction.

Workflow code can express branches, loops, and waits in ordinary sequential
form while the execution survives the loss of the process running that code.
The SDK supplies the durable operations. Using `async` and `await` alone does
not make an arbitrary function durable.

## Clients, Service, and Workers

There are three main parts to a Temporal application:

- A **Client** starts an execution or sends it a message.
- The **Temporal Service** records history, manages timers, and dispatches
  tasks through named Task Queues.
- Your **Workers** poll those queues, execute Workflow and Activity code, and
  report results to the Service.

A Worker can host both Workflow and Activity code, or you can deploy and scale
them separately. [Task Queues](https://docs.temporal.io/task-queue) route work to
compatible [Workers](https://docs.temporal.io/workers); a queue name does not
identify a particular machine. Workflow Tasks advance orchestration. Activity
Tasks execute Activities.

The [hosting choices](https://docs.temporal.io/temporal#what-is-the-temporal-platform)
are a self-hosted open-source Service or **Temporal Cloud**, which operates the
Service for you. In either case, you deploy and operate the Workers that run
your application code. The local development server packages the Service for
experimentation; a production self-hosted deployment has a larger operational
footprint.

## Event History

The Service keeps an [**Event History**](https://docs.temporal.io/workflow-execution/event)
for each execution: an ordered record of durable events such as an Activity
being scheduled, its completed result, a timer starting, or external input
arriving. History records execution progress; it does not store a dump of the
worker's memory.

A completed Activity result can be reused after the Temporal Service records
it. For example, a recorded reservation result remains available to a later
worker. Event History is ordered within an execution's run. It does not record
every log message, variable assignment, or failed Activity attempt.

## Workflow replay and determinism

[**Replay**](https://docs.temporal.io/workflows#how-workflow-replay-works)
reconstructs Workflow state by running Workflow code against recorded Event
History. Suppose `reserveInventory` returned `reservation-42`, the Service
recorded its completion, and the worker then disappeared. A replacement worker
can run the Workflow code from the beginning. At the completed Activity, the SDK
supplies the recorded result, reconstructing the `reservation` variable before
continuing to the next operation. Workers may also use cached Workflow state
rather than replaying the entire history on every task.

Replay requires **deterministic Workflow code**: the same recorded history must
produce a compatible sequence of commands. The
[determinism constraints](https://docs.temporal.io/workflow-definition#deterministic-constraints)
require external I/O, including direct network calls, to stay in Activities.
Workflow code uses the SDK's Workflow APIs for durable waits and replay-safe
behavior. Changing Activity order while old executions are running can break
replay.

## Activity retries and timeouts

An Activity attempt can fail or stop reporting a result. Activity [retry policies](https://docs.temporal.io/encyclopedia/retry-policies)
control repeated attempts, backoff, and non-retryable errors. A temporary outage
may justify another attempt, while an invalid order may require an explicit
business failure. Configure the policy for the operation. Activities retry by
default; Workflow Executions do not have a retry policy by default.

Two timeout boundaries are useful to distinguish:

- **Start-to-Close** bounds one Activity attempt after a worker starts it.
- **Schedule-to-Close** bounds the whole Activity execution, including queue
  waiting, retries, and backoff.

If a worker crashes during an Activity, the Service may need a timeout to detect
the missing result; it does not immediately learn that the process died.
Long-running Activities can report progress through heartbeats. A configured
heartbeat timeout can support faster failure detection. The
[Activity failure detection](https://docs.temporal.io/encyclopedia/detecting-activity-failures)
documentation explains these timeout boundaries.

For example, an Activity retry policy might permit three total attempts, with
a one-second first backoff and a two-second second backoff. These are
illustrative settings, rather than Temporal defaults. After the retry budget
is exhausted, the Workflow must decide how to handle the failure.

## Task Queue dispatch

Timeouts and retries govern failed attempts. Task Queues determine which
compatible workers can receive pending tasks. Workers poll a named Task Queue
through the Service. Several workers with compatible registered code can poll
the same queue, so dispatch does not depend
on one permanent application process. Additional workers provide capacity and
allow pending work to continue when a worker goes offline.

Pending work and in-progress Activities have different recovery paths. If an
Activity's worker disappears, timeouts and retry policy govern when another
attempt can run. Workflow Tasks and Activity Tasks also use separate logical
queue types, even when they share a queue name. This
[Task Queue behavior](https://docs.temporal.io/task-queue) does not guarantee
that all application work executes in arrival order.

## Activity idempotency

An external operation can succeed before Temporal records the Activity's
completion. For example, a payment provider may accept a charge, but the worker
may crash before reporting success. Temporal has no recorded completion to
reuse, so the Activity can run again and repeat the charge.

[**Idempotent** Activities](https://docs.temporal.io/activity-definition#idempotency)
preserve the intended business result when an operation repeats. Techniques
include a stable operation key that the provider durably deduplicates, a
database constraint, or a guarded update. The key's scope and the destination's
deduplication contract must cover the retries the application needs to tolerate.

When retrying the same logical charge, an application can send the same stable
operation key and rely on the provider to recognize the repeated request. Without
that deduplication, the retry can create a second charge. Durable Workflow
execution does not give arbitrary external APIs exactly-once effects.

## Durable timers

A subscription process may wait days for renewal. If the application represents
that wait only with a sleeping process, the waiting point depends on the
process staying alive. Temporal's [**durable timers**](https://docs.temporal.io/develop/typescript/workflows/timers)
preserve that waiting point outside the application process.

The SDK's `sleep` operation records a timer through the Service without reserving
a worker thread for the entire wait. A worker can stop while the timer is
pending. The execution can continue after a compatible worker returns.

Timer expiry and subsequent Workflow execution are separate events. The Service
can record the timer firing while the worker is absent. A returning worker
must run the next piece of Workflow code. The timer neither keeps a sleeping
process alive nor makes an unavailable dependency execute.

## Signals and asynchronous input

An onboarding process may need approval hours after it starts. A
[**Signal**](https://docs.temporal.io/develop/typescript/workflows/message-passing#signal-handlers)
delivers an asynchronous message to a running Workflow, such as
`approve(orderId)`. A Signal handler can change a condition that the Workflow
is waiting on.

The Service records an accepted Signal before a worker necessarily processes
it. If every worker is offline, the message can be durable while the Workflow
is still waiting for a worker to handle it.

Recorded approval can wait for later worker execution, so the human and the
application worker do not need to be active at the same instant. The
application must still define who may send approval and what that approval
means for the business process.

## Parallel Activities and joins

Independent Activities, such as inventory reservation and a risk check, can be
scheduled before the Workflow waits for their results. A join then waits for
both required results before continuing. TypeScript Activity proxy calls return
Promises, so `Promise.all` can express this successful join. The
[parallel execution](https://docs.temporal.io/design-patterns/parallel-execution)
guide describes this pattern.

One completed Activity does not release a join that requires both results.
Worker capacity and external services determine how much the Activities overlap.
Failure handling remains explicit: a rejected `Promise.all` does not
automatically undo external work or cancel every other operation.

## Sagas and compensating actions

A provisioning failure after inventory reservation and payment may require a
refund and inventory release. These **compensating actions** are often organized
as a **Saga**.

Compensation consists of application-defined business operations. A refund
does not erase the original charge as an atomic database rollback would; it
creates a new operation that can also fail. It may need its own retry policy or
human intervention. [Temporal's compensation explanation](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)
describes this distinction.

An execution can preserve outstanding cleanup work. The application still needs
a policy for completing that work or escalating it for intervention.

## Workloads that need durable coordination

I would consider Temporal when coordinating recovery becomes a substantial part
of the application. The following processes are candidates to evaluate; their
categories alone do not establish a need for a workflow engine:

| Process                     | What needs to survive                                                    |
| --------------------------- | ------------------------------------------------------------------------ |
| Order fulfillment           | Payment succeeds while provisioning is temporarily unavailable           |
| Account onboarding          | Several services and a human approval must finish                        |
| Infrastructure provisioning | Resource creation needs retries and cleanup after partial success        |
| Document processing         | A long job has independent steps and unreliable external services        |
| Subscription lifecycle      | Reminders and renewals wait days between operations                      |
| AI tool orchestration       | Model calls and tools need retries, recorded results, and approval gates |

Temporal's documented [use cases](https://temporal.io/#common-patterns-and-use-cases)
include orders, human input, infrastructure, and AI workflows. These processes
coordinate work over time and across failure boundaries.

My adoption test is whether I can identify the business process, its stable
identity, its waiting points, and its recovery rules. A short request handled by
one database transaction may already have sufficient recovery guarantees. A
queue may adequately serve an independent background job. A streaming
computation over millions of records has different requirements. I would test
these design judgments against the actual workload.

## Run a local recovery experiment

The local experiment stops a worker during an order's durable wait, then
restarts it and inspects the same execution's history. The lab is in
`examples/temporal-intro` in [this blog's source code](https://github.com/wcygan/wcygan.net).
Its Activities simulate reservation and fulfillment; they do not call payment
systems or provision real resources.

Use a local checkout of the repository and Node.js 22 or 24. On macOS, install
the CLI through Homebrew. Downloads for other platforms are listed in the
[official TypeScript setup guide](https://docs.temporal.io/develop/typescript/set-up-your-local-typescript).

```sh
brew install temporal
cd examples/temporal-intro
npm ci
```

In one terminal, start the Service with a file-backed development database:

```sh
temporal server start-dev --db-filename ./temporal.db
```

The [CLI development server](https://docs.temporal.io/cli/command-reference/server#start-dev)
listens on `localhost:7233` and serves the Web UI on `http://localhost:8233` by
default. The database flag preserves the lab's state across Service restarts;
without it, the default development database is in memory. Use this server for
local development.

In another terminal, from the same lab directory, start your worker:

```sh
npm run worker
```

Then start one order with a 60-second durable wait:

```sh
npm run order -- order-001 60
```

The Workflow coordinates reservation, a durable wait, and fulfillment:

```ts
import { proxyActivities, sleep } from "@temporalio/workflow";
import type * as activities from "./activities";

const { reserveInventory, fulfillOrder } = proxyActivities<typeof activities>({
  startToCloseTimeout: "10 seconds",
  scheduleToCloseTimeout: "1 minute",
  retry: { maximumAttempts: 3 },
});

export async function orderWorkflow(orderId: string, waitSeconds = 30) {
  const reservation = await reserveInventory(orderId);
  await sleep(waitSeconds * 1_000);
  return fulfillOrder(orderId, reservation);
}
```

`proxyActivities` creates the SDK calls used by Workflow code. The worker
registers the Activity implementations, and `sleep` records the durable timer.
The lab's README contains the complete worker and client setup. The
[TypeScript application basics](https://docs.temporal.io/develop/typescript/core-application)
guide explains that setup.

Test worker recovery during the durable wait:

1. Open the Web UI and select `order-001` in the default Namespace. Confirm that
   reservation completed and a timer started.
2. Stop the worker with `Ctrl+C` during the wait. Leave the Service running.
3. Let the timer expire. The execution cannot run fulfillment without a worker.
4. Start `npm run worker` again. Fetch the same execution's result and history:

```sh
npm run result -- order-001
npm run history -- order-001
```

Inspect the history for a completed reservation, `TimerStarted`, `TimerFired`,
and subsequent fulfillment. The replacement worker should reconstruct state
using the recorded reservation result. Inspect the same execution ID to test
recovery of existing work. Use a fresh ID, such as `order-002`, for a separate
run of the experiment.

This experiment tests recovery after a completed Activity and during a durable
wait. Testing duplicate effects requires a separate interruption after an
Activity's external operation succeeds but before Temporal records completion.

In the local run for this draft, I killed the worker during a 30-second wait.
The history recorded `TimerFired` while the worker was offline. After I restarted
the worker, the same execution completed with one recorded reservation
completion and one recorded fulfillment completion. The restarted worker ran
fulfillment without repeating reservation.

## Adoption and operational checks

I would use Temporal to coordinate a business process's lifecycle: completed
work, waiting points, next actions, and cleanup. Before adopting it, I would test
one representative process under these conditions:

- Restart workers during Activities and waits, and check the resulting history.
- Make a dependency unavailable long enough to exhaust the intended retry
  budget, then inspect the business outcome.
- Prove duplicate requests are safe at the actual external destination.
- Change Workflow code while old executions exist, using a deliberate deployment
  and versioning strategy. [Safe deployments](https://docs.temporal.io/develop/safe-deployments).
- Check history growth for a process that loops indefinitely. **Continue-As-New**
  can start a new run with carried-forward state and a fresh history.
  [Continue-As-New](https://docs.temporal.io/develop/typescript/workflows/continue-as-new).

I would also assign responsibility for operating the Service, scaling the
workers, and responding when a process needs intervention. My acceptance
criteria would be a process whose behavior I can explain after failure and a
recovery path I have tested.
