**Kafka stores a shared event history that applications can read independently.**
Shipping, fraud checks, and analytics can process the same order events at
different speeds.

## Records, topics, and partitions

A **producer** writes event records to Kafka, and a **consumer** reads them.

### Record

A [**record**](https://kafka.apache.org/43/getting-started/introduction/#main-concepts-and-terminology)
describes one event. It has a value and a timestamp, and can also carry a key
and headers. In record A, the key identifies an order, and the JSON value names
the event, the order, and when it occurred. That event time can differ from the
Kafka record timestamp. Kafka also supports encodings other than JSON.

<KafkaRecordFigure />

### Topic

A **topic**, such as `orders`, names a stream of records. It can contain several
kinds of order events: an order can be placed, paid, shipped, or cancelled.
Record A is one of the six example records in this topic.

<KafkaTopicFigure />

### Partitions

A topic contains one or more **partitions**. Each partition is an ordered log;
a new record is appended to one of those logs. An **offset** identifies a
record's position within its partition.

The demo uses a separate set of order records to show how routing places them
in partitions.

<KafkaPartitioningDemo />

## Keyed partition routing

A record can carry a **key**, such as an order ID, to group related events.
Records with matching keys share a partition. Each partition has its own
offsets, and Kafka guarantees order **within a partition**.

By default, when no partition is specified and keys are not ignored, the Java
producer hashes the serialized key with Murmur2, clears the sign bit, and takes
the remainder modulo the partition count. The demo uses UTF-8 keys and three
partitions by default. Keyed routing remains stable while the partition count and routing
strategy stay fixed. Changing either can map a key to a different partition. See
[producer routing](https://kafka.apache.org/43/configuration/producer-configs/#producerconfigs_partitioner.class).

### Hot keys and uneven load

A busy key concentrates work in one partition. That partition can become a
bottleneck while others have less work to process. Key selection must balance
the application's ordering requirements with the need to distribute work.

<KafkaHotKeyDemo />

### Partition placement across brokers

A **broker** is a Kafka server. Each partition has a **leader** on a broker that
handles writes to that partition. Placing partition leaders on different brokers
distributes their work across machines.

In the demo, a producer sends each record to the broker leading its selected
partition. The Rust producer uses librdkafka's
[`murmur2_random` partitioner](https://github.com/confluentinc/librdkafka/blob/master/CONFIGURATION.md)
to match the Java-compatible hashing shown above. The demo assumes a replica of
P0 is available on each broker. Moving P0's
leader changes which broker handles its writes; it does not change the partition
selected for a key. The log shown after a move represents the new leader's
existing copy.

<KafkaBrokerPlacementDemo />

## Replication and broker failures

A partition's **replicas** are copies of its log stored on brokers. Kafka tracks
which replicas are **in sync** with the partition leader. With `acks=all` and
`min.insync.replicas=2`, a successful write requires at least two in-sync copies.
Kafka's leader elections also account for
[eligible leader replicas](https://kafka.apache.org/43/operations/eligible-leader-replicas/).
Kafka's [KRaft controllers](https://kafka.apache.org/43/operations/kraft/) manage
cluster metadata and elections. Brokers store the event records.

## Retained records

Reading a record does not remove it from Kafka. Consumers can read the same
retained history independently, with each tracking its own position.

## Retention and compaction

**Delete retention** limits retained history by age or size. **Compaction**
eventually keeps the latest value for each key.

[Cleanup runs in the background](https://kafka.apache.org/43/design/design/#log-compaction).
A topic can combine both policies. Retention determines which earlier records
remain available to consumers.

## Independent processing

When Kafka is available, checkout can publish an order event and finish before
analytics processes it. The services can make progress at different rates.

## Consumer groups

Each **consumer group** reads the whole stream independently of other groups.
Within a regular group, members divide the partitions. With three partitions
and four members, one member stays idle because there is no fourth partition
to assign.

These partition-assignment rules apply to regular consumer groups. Kafka's
[share groups](https://kafka.apache.org/43/javadoc/org/apache/kafka/clients/consumer/KafkaShareConsumer.html)
have different work-sharing rules.

## Committed offsets and replay

A **committed offset** records the next position to read. After a restart, the
consumer resumes from that saved checkpoint. To replay, the consumer returns
to an earlier position in the log. Only records still retained are available.

A crash can cause the consumer to process a record again. External effects
therefore need **idempotency**: repeating an operation must be safe. Kafka's
[exactly-once guarantees](https://kafka.apache.org/43/design/design/#message-delivery-semantics)
apply to defined workflows; payments and emails need their own handling at the
external system boundary.

## Consumer lag

A saved checkpoint tracks progress; it does not guarantee that a consumer keeps
pace with producers. Records accumulate behind a consumer that processes them
more slowly than producers write them. The log buffers that work, but available
storage and retention limit how far the consumer can fall behind.

## Stream processing and integration

| Problem                                    | What a stream enables                       |
| ------------------------------------------ | ------------------------------------------- |
| Several services need each order           | Independent readers                         |
| Search or analytics needs database changes | [Change data capture](/change-data-capture) |
| Totals need to stay current                | Continuous aggregation                      |
| Measurements need later analysis           | Retained telemetry                          |

[Streams](https://kafka.apache.org/43/streams/introduction/) is an application
library that processes events. [Connect](https://kafka.apache.org/43/kafka-connect/overview/)
moves data through configured connectors. Kafka brokers store the records that
these applications and connectors exchange.

## Run Kafka locally

This single-broker lab demonstrates independent consumers and replay. You need
Docker and an available port `9092`. The commands use the official
`apache/kafka:4.3.1` image and follow the
[quickstart](https://kafka.apache.org/quickstart/).

### Start a broker and create a topic

```sh
docker run -d --name kafka-lab \
  -p 127.0.0.1:9092:9092 apache/kafka:4.3.1
```

Check whether the broker is ready. If it is still starting, repeat the command
after a few seconds:

```sh
docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
```

Create `orders` with three partitions, then inspect it:

```sh
docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create --topic orders \
  --partitions 3 --replication-factor 1

docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic orders
```

### Write six keyed records

In Bash or Zsh, send six records. Each line contains a key before the first
colon and a value after it:

```sh
docker exec -i kafka-lab /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic orders \
  --reader-property parse.key=true --reader-property key.separator=: \
  --command-property acks=all <<'EOF'
order-101:{"event":"OrderPlaced","orderId":"order-101","amount":42}
order-102:{"event":"OrderPlaced","orderId":"order-102","amount":18}
order-101:{"event":"OrderPaid","orderId":"order-101","amount":42}
order-103:{"event":"OrderPlaced","orderId":"order-103","amount":73}
order-102:{"event":"OrderPaid","orderId":"order-102","amount":18}
order-103:{"event":"OrderPaid","orderId":"order-103","amount":73}
EOF
```

### Read the history with two consumer groups

Run the analytics consumer. It prints six records and exits:

```sh
docker exec kafka-lab /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic orders \
  --group analytics --from-beginning --max-messages 6 \
  --command-property enable.auto.commit=true \
  --formatter-property print.key=true \
  --formatter-property print.partition=true \
  --formatter-property print.offset=true
```

Repeat the command with `--group fulfillment`. This group also reads all six
records. Compare the order within each partition: records from different
partitions may interleave differently, and different keys can share a partition.

Inspect the saved group progress:

```sh
docker exec kafka-lab /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group analytics
```

Compare `CURRENT-OFFSET`, `LOG-END-OFFSET`, and `LAG` to inspect the group's
progress. The consumer's `--from-beginning` option applies only when no usable
committed offset exists. An existing checkpoint takes precedence.

### Replay an existing group

With the analytics consumer stopped, preview its offset reset:

```sh
docker exec kafka-lab /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group analytics --topic orders \
  --reset-offsets --to-earliest --dry-run
```

Then apply the reset:

```sh
docker exec kafka-lab /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group analytics --topic orders \
  --reset-offsets --to-earliest --execute
```

Run the analytics consumer again to reread all six records.
[Offset resets](https://kafka.apache.org/43/operations/basic-kafka-operations/#managing-consumer-groups)
require an inactive group. Replaying the records also repeats the application's
effects.

Remove this lab's container and its temporary data when finished:

```sh
docker rm -f -v kafka-lab
```

## When Kafka fits

Use Kafka when multiple applications need independent access to a durable event
history. For a small workflow, an API call, database table, or task queue may be
simpler to operate.

The local lab exercises the requirements Kafka addresses: publishing an event
once, reading it in two independent groups, and replaying retained history.

For more detail, see [Kafka's introduction](https://kafka.apache.org/43/getting-started/introduction/),
[use cases](https://kafka.apache.org/43/getting-started/uses/), and
[partitioning](https://kafka.apache.org/43/design/protocol/#partitioning-and-bootstrapping).
