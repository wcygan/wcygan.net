[celld](https://github.com/denoland/celld) runs small, named JavaScript servers with persistent state on machines you operate. If I already have an S3-compatible object store, it gives me a way to use that store as the backing for stateful applications.

The runtime implements Cloudflare's Durable Objects programming model. A chat room, collaborative document, or agent session can have its own JavaScript handler and SQLite database. celld locates the object's current owner and preserves its writes.

A stateful service needs both storage and a rule for who can change it. A JavaScript variable disappears when its process restarts, and running more processes creates separate copies of that variable. An object store preserves bytes, but does not supply the application's execution environment or decide which process may update its state. celld supplies that runtime and ownership protocol.

This draft follows [v0.6.1](https://github.com/denoland/celld/releases/tag/v0.6.1), a **beta** release, researched on October 1, 2026.

## Cells, nodes, and fleets

A **cell** is celld's name for a Durable Object: an addressable unit of application logic with private storage. It follows the **actor** pattern: callers send messages to a named object, and the object manages its own state. A **node** is one celld process. Nodes using the same fleet bucket or bucket prefix form a **fleet**.

For example, three named counters can each own a separate SQLite database. Incrementing `room:blue` changes that cell's counter while the other two retain their values. An acknowledged database write can survive a runtime restart; temporary JavaScript memory cannot.

A chat application can assign each room a cell named `room:blue`, `room:green`, or `room:red`. A stateless Worker receives an HTTP request, derives the cell's ID, and calls it. If another node owns the cell, the receiving node can forward the call to that owner. The application addresses the room by name without tracking its current machine. [The cell API](https://github.com/denoland/celld/blob/v0.6.1/docs/services/durable-objects.md) provides the `idFromName()` and `get()` operations.

Each cell runs JavaScript on one thread. That simplifies reasoning about synchronous storage operations, but an `await` can allow handlers to interleave unless an input gate prevents it. “One writer” does not make every asynchronous handler an indivisible transaction.

## Cell boundaries and workload fit

The cell's name identifies both its request handler and its private state. That boundary fits a unit whose state the application can mostly manage independently.

| Workload                   | Possible cell key | What the cell owns                        |
| -------------------------- | ----------------- | ----------------------------------------- |
| Chat or a multiplayer room | Room ID           | Membership, messages, game state          |
| Collaborative editing      | Document ID       | Document changes and connected clients    |
| Agent sessions             | Session ID        | Inbox, persisted memory, scheduled work   |
| Shopping carts             | User ID           | One user's cart and reservations workflow |
| Device coordination        | Device ID         | Configuration and recent device state     |

These workloads require application code; they are not built-in features. An alarm can schedule future work, and WebSockets can keep clients connected. The application still defines authentication, message semantics, and reconnect behavior.

The cell key determines how the application can distribute its work. One globally shared cell remains one writer after adding machines, while independent cells can run in parallel. State that spans several cells requires explicit coordination; private SQLite databases do not supply a global SQL transaction. [The programming model](https://github.com/denoland/celld/blob/v0.6.1/docs/README.md#what-do-you-build-with-cells) fits workloads that divide along these boundaries.

Adding a node provides more capacity, but does not immediately split a hot cell into smaller writers. Cell ownership can move between machines. An idle cell can be **[hibernated](https://github.com/denoland/celld/blob/v0.6.1/docs/services/durable-objects.md#ownership-and-the-single-threaded-model)**: celld removes it from memory, and its constructor runs again at the next event. The current balancer moves only hibernated cells and counts cells relative to node weight. It does not measure each cell's CPU demand. These [placement limits](https://github.com/denoland/celld/blob/v0.6.1/docs/limitations.md#fleets) affect how a workload uses that capacity.

For an application with many relational joins and transactions across users, a shared PostgreSQL database may be a better fit. I would start with celld when named objects simplify the application and I want to operate the runtime myself.

## JavaScript execution and SQLite storage

Each independent cell needs an execution environment and persistent storage. Three components provide them:

- **V8** executes the JavaScript application.
- **SQLite** holds each cell's database on its owning node.
- **LTX** describes committed changes to SQLite pages for replication and recovery.

The bucket holds deployments, ownership records, and durable storage data. SQL operations run against the cell's local database; the bucket does not execute SQL. During recovery, a large database can fetch pages on demand. [The storage contract](https://github.com/denoland/celld/blob/v0.6.1/docs/guarantees.md#epoch-chain-restore) describes how epochs and page data support restoration.

LTX replicates changes at the page level. Suppose a database baseline is already stored and a later transaction changes SQLite pages 2 and 5. LTX carries new images of those pages, with transaction and checksum metadata. It does not represent row-level events or contain only the changed bytes. Initial snapshots and later compaction can contain more pages; the page numbers in this example depend on the write.

celld also implements Workers bindings for KV, D1, Queues, R2, Workflows, and other services. A cell backs each D1 database or KV namespace. An R2 binding accesses objects in the fleet bucket; it does not make celld a public S3 server. The [compatibility matrix](https://github.com/denoland/celld/blob/v0.6.1/docs/cloudflare-compat.md) lists support for the APIs an application may use.

## Ownership, leases, and fencing

The local SQLite database belongs to the cell's current owner. Nodes coordinate which node may serve that cell through the bucket. A node claims a cell by conditionally creating or updating its ownership record. A **compare-and-swap** operation applies an update only if the record still matches the version the node read. When the store implements that operation correctly, two competing nodes cannot both win the same update.

A node's **lease** limits how long it can retain authority without renewal. If it loses that authority, it fences itself by stopping cell service and exiting. Each activation also receives a new **epoch**, a numbered generation with its own LTX storage prefix. The separate prefix prevents a stale process from overwriting the new owner's storage lineage. [Ownership and fencing](https://github.com/denoland/celld/blob/v0.6.1/docs/guarantees.md#the-ownership-record) depend on the bucket's actual behavior.

celld therefore does not require a separate consensus service, but it still relies on coordination supplied by the object store. If the store ignores conditional writes, the ownership guarantee breaks.

## Write acknowledgment and durability proofs

Ownership determines which node may write. Before that node returns a successful response, celld must also obtain a durability proof covering the writes the response can reveal. It can obtain that proof through two paths:

1. **One node:** the write waits for bucket storage before the response can succeed.
2. **Multiple nodes, with a healthy follower ensemble:** the ensemble is a group of peer nodes that persist the change to disk before acknowledgment; bucket upload can finish later. An `fsync` asks the operating system to persist file data. A peer copy is a log copy, not another concurrently writable cell.

The default fleet mode recruits up to two followers. A fleet proof requires every member of the current follower ensemble to persist the write. Without a usable ensemble, celld falls back to a bucket proof. Adding a second node can therefore change which storage operations a write waits for, as well as adding compute capacity. The [acknowledgment rules](https://github.com/denoland/celld/blob/v0.6.1/docs/guarantees.md#the-acknowledgement-rule-rpo0) describe these requirements.

With a fleet proof, **the bucket may not yet contain every acknowledged write**. Until upload completes, durability also depends on persistent peer disks.

## Owner recovery and failure domains

Before restoring and serving a cell, a replacement must recover the prior owner's log data that has not reached the bucket. On the successful path, it fences the prior log session, collects the complete retained follower tail, uploads the recovered data, and seals the session. It can then claim a new cell epoch and restore the database. An inconclusive peer failure can block completion of this recovery. [The recovery gate](https://github.com/denoland/celld/blob/v0.6.1/docs/guarantees.md#the-takeover-recovery-gate) describes why the current bucket contents alone are insufficient.

A **failure domain** groups resources that can fail together. Stopping one process, rebooting a machine with its disks intact, and permanently losing its disks are different failures. A surviving follower holds recovery data; it does not automatically become a second serving cell.

The project's RPO=0 claim means no loss of acknowledged writes under its durability assumptions. It does not cover losing every relevant disk before upload. The [implementation records possible loss](https://github.com/denoland/celld/blob/v0.6.1/crates/celld/node_log.rs#L5219) when no complete witness survives and the members' outcomes are conclusive. Compute nodes and storage on one physical machine share a failure domain: a second process on that machine cannot protect against losing it.

A timeout does not establish whether a write committed. If a client retries an operation that must take effect once, the operation needs a stable ID and a handler that recognizes duplicates. Recovery alone does not make application effects exactly once.

## Run the counter locally

The official counter example exercises cell naming, persistent storage, and restart behavior without an S3 setup. This release's installer supports Linux x86-64, Linux ARM64, and Apple Silicon. You need Git and a JavaScript package manager to install esbuild.

Download and inspect the [installer](https://celld.dev/install.sh), then install the pinned release:

```sh
curl -fsSL https://celld.dev/install.sh -o install-celld.sh
less install-celld.sh
CELLD_VERSION=v0.6.1 sh install-celld.sh
export PATH="$HOME/.local/bin:$PATH"
celld --version

git clone --depth 1 --branch v0.6.1 https://github.com/denoland/celld.git
cd celld/examples/counter

npm install --no-save esbuild@0.25.12
export PATH="$PWD/node_modules/.bin:$PATH"
esbuild --version
celld dev --port 19876
```

celld uses [esbuild](https://esbuild.github.io/getting-started/) to bundle Worker code, so the executable must be on `PATH`. Leave the server running and send these requests from another terminal:

```sh
curl -sS 'http://127.0.0.1:19876/?name=blue'
curl -sS 'http://127.0.0.1:19876/?name=blue'
curl -sS 'http://127.0.0.1:19876/?name=green'
```

With fresh state, the responses should contain `n` values of **1, 2, and 1**, along with the request URL. The names address independent cells. Stop the server with Ctrl+C, restart it with `celld dev --port 19876`, and request `blue` again. Its value should now be **3**.

I ran this sequence on Apple Silicon with celld 0.6.1 and esbuild 0.25.12. The initial requests returned 1, 2, and 1. After a restart, blue returned 3 and green returned 2. These results verify the local example's persisted state; they do not test distributed failover or an S3 implementation.

The [example Worker](https://github.com/denoland/celld/blob/v0.6.1/examples/counter/index.js) reads the `name` parameter, calls `idFromName(name)`, and forwards the request to the resulting counter. Its `wrangler.jsonc` maps the `COUNTER` binding to the exported class. Editing a source file triggers a rebuild while state remains in `.celld/dev`. To **delete that local test state** and begin again, use `celld dev --clean --port 19876`.

## Test an S3-compatible store

A two-node experiment adds a real bucket. Before starting the nodes, test whether the store meets celld's storage contract:

- Conditional creation and conditional replacement must actually reject conflicting writes.
- Reads must see successful writes, and byte-range reads must return the correct bytes.
- Enabling epoch garbage collection also requires listings to see successful writes.

The [v0.6.1 qualification notes](https://github.com/denoland/celld/blob/v0.6.1/docs/guarantees.md#what-the-bucket-must-provide) report that community MinIO passes the conditional-write test, but celld has not qualified it for production. The notes identify a broken September 6, 2025 release and recommend the September 7 release or later. Qualify the exact build you use; an “S3-compatible” label does not establish these guarantees.

Create a dedicated test bucket and configure credentials through celld's standard AWS credential chain. Replace the endpoint and region below with your store's values:

```sh
export CELLD_BUCKET=s3://celld-lab
export S3_ENDPOINT=https://s3.example.internal
export AWS_REGION=us-east-1

celld diagnose --listen 127.0.0.1:0 --bucket "$CELLD_BUCKET" \
  --endpoint "$S3_ENDPOINT" --region "$AWS_REGION"

# Run from celld/examples/counter, with esbuild on PATH.
celld deploy . --bucket "$CELLD_BUCKET" \
  --endpoint "$S3_ENDPOINT" --region "$AWS_REGION"
```

`diagnose` writes and deletes a small probe object. The ephemeral `--listen` port avoids a collision with a running node. Check for `ok bucket conditional write (create, reject-create, update, reject-stale)`. Nodes also test ranged reads at startup. A successful probe establishes a prerequisite for the lab; it does not fully certify durability.

Start node A with a writable, persistent local state directory:

```sh
CELLD_WATCH=/var/lib/celld/node-a \
celld --bucket "$CELLD_BUCKET" \
  --endpoint "$S3_ENDPOINT" --region "$AWS_REGION" \
  --listen 0.0.0.0:8080 \
  --internal-listen 10.0.0.12:8081 \
  --advertise 10.0.0.12:8081
```

Start the same version on node B with its own persistent directory, the same bucket credentials and deployment, and `10.0.0.13:8081` for both internal addresses. Replace the example private IPs with your machines' addresses. Put the public Worker listener behind your TLS proxy and keep the internal listener on a trusted private network or encrypted overlay. [The security boundary](https://github.com/denoland/celld/blob/v0.6.1/docs/security.md) treats bucket access as fleet administration access.

This fleet procedure follows the documented CLI. I have not run it against a self-hosted S3 service for this draft. Test the fleet in this order:

1. Request the same counter through both nodes and check that they share its value.
2. Repeat the `celld diagnose` command above and inspect peer connectivity.
3. Use the node logs to identify the counter's owner. First try a graceful stop; then, in a separate run of this disposable fleet, kill the owner abruptly with SIGKILL to exercise crash recovery. Preserve its disks, request the cell through the surviving node, and record the interruption and recovered value.
4. Restart the stopped node. Repeat with a peer temporarily unreachable to distinguish retrying recovery from ordinary owner takeover.
5. Compare write latency with one and two nodes, recording your endpoint, hardware, workload, and durability mode.

Run real nodes under a restart supervisor, as required by the [operating contract](https://github.com/denoland/celld/blob/v0.6.1/docs/guarantees.md#the-supervisor). A successful lab run does not establish a recovery-time guarantee.

## Adoption criteria and operating responsibilities

celld appeals to me when named objects simplify a stateful service and I want control of its machines and storage. That control comes with responsibility for the runtime, private network, durable disks, bucket semantics, backups, upgrades, and ingress.

Before adopting it, I would test a workload with a clear cell boundary, check its required Cloudflare APIs against the compatibility matrix, and run failure experiments on the actual storage backend. I would evaluate whether its state survives the intended failures, its latency meets the workload's needs, and its operating requirements are manageable.
