[Apache Flink](https://flink.apache.org/) processes events as they arrive and
retains state between records. That state lets a job update a revenue total,
detect patterns in account activity, or track device alerts. After a failure,
Flink can recover the state and resume processing.

## Sources, operators, and sinks

A Flink [dataflow](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/learn-flink/overview/)
connects three roles: a **source** reads records, an **operator** transforms them,
and a **sink** receives the results. For a purchase-totaling job, the source
reads purchases and the operator updates each customer's total.

## Bounded and unbounded input

A **bounded** input has a known end, such as a fixed file of purchases. An
**unbounded** stream can keep receiving records. Flink handles both, but its
[batch execution mode](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/execution_mode/)
requires bounded input.

An ongoing aggregate can emit revised results as more records arrive. A
[dynamic table](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/concepts/sql-table-concepts/dynamic_tables/)
represents those changing results; the sink must support the updates it receives.

## JobManager and TaskManagers

Flink's [runtime architecture](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/concepts/flink-architecture/)
separates coordination from execution. The **JobManager** coordinates the job.
**TaskManagers** execute its tasks, retain working state, and exchange records.
An operator can have multiple parallel **subtasks**, each handling part of the
job's work.

## Keyed state

Each subtask can retain **state**: information kept between records. With
[keyed state](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/fault-tolerance/state/),
`keyBy(customer)` routes a customer's records to one operator subtask. That
subtask owns the customer's count and updates it as purchases arrive.

### Keyed shuffles

Purchases for one customer can arrive at different sources. A **shuffle**
redistributes the records so that the same customer's purchases reach the same
subtask. This routing creates a
[keyed stream](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/learn-flink/overview/#keyed-streams).

### Hot keys and workload skew

If most purchases belong to one customer, the subtask that owns that key receives
most of the work. The other subtasks cannot share those updates merely because
they have spare capacity.

## Event enrichment with broadcast state

A purchase-totaling job may also need reference data, such as each customer's
region. [Broadcast state](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/fault-tolerance/broadcast_state/)
lets the job retain customer-region updates and attach the known region to each
purchase. A later region update changes the output for future purchases.

## Event time and watermarks

A revenue calculation may need totals for a time interval. A **window** groups
purchases for that calculation. **Event time** is the time a purchase happened;
it can differ from the time the record arrives. A
[**watermark**](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/concepts/time/)
communicates progress in event time so the job can close windows under its chosen
lateness policy.

Older events can still arrive after a watermark passes their timestamps. A job
can discard a late purchase, retain it, or revise the window's result, depending
on its lateness policy.

## Backpressure

As the job processes purchases, a sink may receive records faster than it can
write them. Buffered records accumulate, and a full buffer slows upstream work,
eventually slowing the source. This propagation is
[**backpressure**](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/ops/monitoring/back_pressure/).

## Checkpoints and barrier alignment

The counts and reference data retained by operators need a recovery path when a
worker fails. A **checkpoint** saves source progress and operator state together.
[Checkpoint barriers](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/concepts/stateful-stream-processing/#barriers)
mark that snapshot in the input streams. For an **aligned** checkpoint, an input
waits at its barrier until matching barriers arrive on the other inputs.

### Checkpoint recovery and source replay

After a worker fails, Flink restores a completed checkpoint and replays the
records that followed it. Recovery therefore requires a source that supports
replay.

This recovery path requires
[checkpointing to be enabled](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/fault-tolerance/checkpointing/).
The checkpoint storage must survive the failures the job needs to recover from.

### Exactly-once state and external writes

An **exactly-once** state guarantee means each record affects the recovered
operator state once, even if recovery replays the record. That guarantee does not
automatically make an external write happen once. The
[sink's guarantees](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/learn-flink/fault_tolerance/#exactly-once-guarantees)
remain part of the result. Replaying a record can repeat a blind append to an
external sink. An **idempotent** write preserves the same effect when repeated.

## Stateful processing use cases

| Incoming events  | Remembered context  | Result           |
| ---------------- | ------------------- | ---------------- |
| Purchases        | Window totals       | Live revenue     |
| Account activity | Recent patterns     | Fraud signals    |
| Device readings  | Last report, timers | Alerts           |
| Database changes | Reference data      | Enriched records |

These [use cases](https://flink.apache.org/what-is-flink/use-cases/) depend on
**state, time, parallelism, and recovery** as part of the computation. Those needs
can justify Flink; a database query or small consumer may already be enough for
a simpler workload.

## Run Flink locally

The companion lab in `examples/flink/` runs Flink **2.3.0** with Docker Compose.
The lab's batch totals, new-file discovery, checkpoints, and worker recovery were
verified on Linux ARM64.

You need Docker with Compose and a few GB of memory allocated to Docker. Run
these commands from the repository root:

```sh
cd examples/flink
docker compose up --build -d
curl -fsS http://localhost:8081/overview
```

Repeat `curl` until the response reports one TaskManager and two slots, then
open the [dashboard](http://localhost:8081).

**Run a bounded aggregation**

The batch script counts purchases and totals their amounts per customer:

```sql
SELECT customer, COUNT(*), SUM(amount_cents)
FROM orders
GROUP BY customer;
```

Run the script once per clean lab. Repeated runs append more output files.

```sh
docker compose run --rm sql-client \
  /opt/flink/bin/sql-client.sh -f /lab/sql/batch.sql
docker compose exec -T taskmanager \
  sh -c 'cat /lab/state/output/batch/part-* | sort'
```

The output columns are `customer,order_count,total_cents`. Expect these rows:

```text
alice,3,3500
bob,2,1500
carol,1,525
```

**Process arriving files**

The streaming query lowercases customer names and keeps orders with positive
amounts:

```sql
SELECT order_id, LOWER(customer), amount_cents
FROM arriving_orders
WHERE amount_cents > 0;
```

Submit the job, then publish a complete input file under a new path:

```sh
docker compose run --rm sql-client \
  /opt/flink/bin/sql-client.sh -f /lab/sql/streaming.sql
docker compose exec -T taskmanager sh -c \
  'cp /lab/data/orders.jsonl /lab/state/input/.orders.pending &&
   mv /lab/state/input/.orders.pending /lab/state/input/orders-001.jsonl'
```

Wait about 15 seconds, then inspect the six finished rows:

```sh
docker compose exec -T taskmanager \
  sh -c 'cat /lab/state/output/streaming/part-* | sort -t, -k1,1n'
```

Publish the second file while the same job keeps running:

```sh
docker compose exec -T taskmanager sh -c \
  'cp /lab/data/new-orders.jsonl /lab/state/input/.new-orders.pending &&
   mv /lab/state/input/.new-orders.pending /lab/state/input/orders-002.jsonl'
```

After another short wait, repeat the output command. Expect eight rows,
including `7,carol,1000` and `8,bob,300`. The output has lowercase names and
excludes the order with a negative amount.

The [filesystem source](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/connectors/table/filesystem/#directory-watching)
discovers new immutable paths; editing a previously discovered file does not
supply new input. The lab's five-second checkpoints finalize rolled output files
in the [file sink](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/connectors/datastream/filesystem/#part-file-lifecycle).

**Recover a failed worker**

Wait for eight output rows and a completed checkpoint in the dashboard:

```sh
docker compose restart taskmanager
```

After the worker restarts, the job should return to **RUNNING**, show a restored
checkpoint, and retain eight output rows without duplicates. This recovery test
keeps the JobManager and shared volume alive. Restarting the whole stack requires
resubmitting jobs.

See `examples/flink/README.md` for the full expected output and additional
exercises. Remove the lab containers and scratch data when finished:

```sh
docker compose down --volumes --remove-orphans
```

For more practice, use the [SQL tutorial](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/getting-started/quickstart-sql/)
or [operations playground](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/getting-started/flink-operations-playground/).
