[ClickHouse is a column-oriented SQL database for analytical queries](https://clickhouse.com/docs/get-started/about/intro).
It filters, groups, and summarizes large datasets. I want to understand which
workloads benefit from that design, what it costs to operate, and how to try it
on my own computer.

The [open-source repository](https://github.com/ClickHouse/ClickHouse) is licensed
under Apache 2.0. [ClickHouse Cloud](https://clickhouse.com/docs/cloud) is a managed
offering around the database. This post uses the open-source server locally,
with web events as the running example: a time, country, event type, and revenue
in integer cents.

## Transactional and analytical workloads

A **transactional** workload, often called OLTP, typically retrieves or changes a
small number of records. An application asking “What is the current state of
order 104?” may also need to change several records in one transaction.

An **analytical** workload, often called OLAP, examines many records and returns a
small summary. “How many purchases did we receive in each country last week?”
requires aggregating events across that period. ClickHouse targets this access
pattern. [The introduction compares these workloads](https://clickhouse.com/docs/get-started/about/intro).

I would investigate ClickHouse for:

- **Product analytics:** grouping page views, signups, and purchases by time,
  customer, or feature.
- **Observability:** searching structured logs and computing error rates or latency
  percentiles across many requests.
- **Usage reporting:** turning an append-heavy event stream into customer-facing
  counts and trends.

These workloads fit its analytical design, but that alone does not establish a
need for ClickHouse. I would first identify the slow query, its data volume, and
how fresh its answer must be. “Real-time analytics” describes both ingestion
latency and query latency; it does not promise a particular latency for my
application.

## Analytics ingestion and query freshness

A common architecture stores operational records in PostgreSQL or MySQL and
sends events or captured changes to ClickHouse. The application database handles
its transactions. ClickHouse runs analytical queries over the data it receives.

Source commits, insertion into ClickHouse, and dashboard refreshes are separate
steps. A query can summarize only the events that have reached ClickHouse. A
dashboard may continue showing an older result until it refreshes. Fast query
execution and fresh data are separate properties.

An insert-only feed still needs retry handling. Change data capture may require
an initial snapshot and a plan for source updates and deletes. Those behaviors
belong to a connector; the open-source server does not automatically watch
another database. The official
[PostgreSQL ingestion guide](https://clickhouse.com/docs/integrations/clickpipes/postgres),
for example, describes ClickPipes, a managed ClickHouse Cloud service. The local
lab below inserts data directly.

## Column-oriented storage

A query over a table with many fields may need only its day and `revenue_cents`.
A row-oriented layout stores each record's fields together. A column-oriented
layout groups values from the same field, so the query can read the columns it
needs.

Logical column selection does not directly predict disk traffic or a speedup
ratio. Physical reads operate on compressed chunks and depend on indexes,
caching, and the execution plan.

## Dictionary encoding and compression

An event table may contain millions of country values but only a few distinct
country codes. `LowCardinality(String)` applies **dictionary encoding**: it stores
the distinct values in a dictionary and represents each row with a reference to
one of them. Each reference decodes to the original value.

The dictionary consumes space too, so encoding does not always produce a smaller
representation. The benefit depends on the values, how often they repeat, and
the surrounding storage format.
[The LowCardinality reference describes its intended use](https://clickhouse.com/docs/reference/data-types/lowcardinality).

Dictionary encoding differs from general compression codecs such as LZ4 or
ZSTD. Grouping similar values creates opportunities for both encoding and
compression. ClickHouse combines these techniques with execution over batches
of values, usually called **vectorized execution**. The mechanisms address
separate costs: reading data, moving data, and executing operations per row.
[The performance overview explains those mechanisms](https://clickhouse.com/docs/get-started/about/why-clickhouse-is-so-fast).

## Data parts and background merges

An **engine** is the storage implementation selected in a table definition.
**MergeTree** is the main storage-engine family. It stores inserted batches as
immutable, sorted **data parts**, each a separately stored group of rows.
Several parts can be active at once, each with its own sorted data and index.
Background merges combine smaller parts into larger parts and replace the
active inputs.
[The parts guide explains their lifecycle](https://clickhouse.com/docs/concepts/core-concepts/parts).

A column-oriented layout also does not require one physical file per column.
ClickHouse supports several physical part formats, including Compact parts that
store columns together in one file.
[The MergeTree reference describes those formats](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree#data-storage).

Rows are queryable before the background merge finishes. Ordinary MergeTree
preserves duplicate rows, so a merge does not automatically deduplicate data.
[The MergeTree reference distinguishes these behaviors](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree).

Many tiny inserts can create too many small parts and increase merge work.
[Batching or asynchronous inserts](https://clickhouse.com/docs/concepts/best-practices/selecting-an-insert-strategy)
can reduce that work. An asynchronous insert can buffer several requests before
writing a part; its acknowledgement and retry settings still matter. The lab
uses explicit batches.

## Sort order and sparse primary indexes

Within a data part, a table's `ORDER BY` determines row order. The lab uses
`ORDER BY (country, event_time)`: rows sort by country, then by time within each
country.

ClickHouse's sparse primary index records keys at intervals rather than for
every row. These entries identify **granules**, groups of rows that might match
a query condition. The query still reads candidate data and applies its filter.
[The primary-index guide walks through this process](https://clickhouse.com/docs/concepts/core-concepts/primary-indexes).

The default row granularity is 8,192, and adaptive sizing also depends on bytes.
The index conservatively selects candidate ranges; the query still needs to
check the rows within them.
[MergeTree documents the storage settings](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree).

Choose the key for the queries the table needs to serve. A leading country key
can help country-filtered queries, but it is not a universal choice for queries
across all countries. ClickHouse's primary key also **does not enforce
uniqueness**: events with the same key can coexist. That differs from the
primary-key contract of a typical transactional table.

## Partitions and data lifecycle

A **partition** groups a table's parts using an expression such as
`toYYYYMM(event_time)`. Monthly partitions make lifecycle operations, such as
removing old data, easier to express. A partition does not imply a separate
server for each month.

A compatible date filter can exclude entire partitions before the query checks
primary-key granules in the remaining parts. Selecting one month changes the
query's candidates; the other months remain stored. Dropping a partition is a
separate operation that removes its data.
[The partition guide explains pruning and data management](https://clickhouse.com/docs/concepts/core-concepts/partitions).

Choose a partition key mainly for data management. Many tiny partitions create
many separate groups of parts. Parts in different partitions cannot merge with
one another. Within each part, the sort key organizes rows for filtering.

## Parallel aggregation

After selecting relevant partitions, granules, and columns, a query processes
the values it reads. A **processing block** is a batch of values moving through
query execution, distinct from a stored data part or granule.

A query that filters purchase events and sums their revenue can compute a
partial sum for each processing block, then combine the partial sums. The
result equals the sum of all matching events.

`SUM` is a decomposable aggregate. An average requires both a sum and a count:
averaging partial averages gives an incorrect result when their groups have
different sizes. Other aggregate functions use their own intermediate states.

ClickHouse can divide query work among multiple processing lanes on one server.
Parallel execution does not require another machine. The actual pipeline depends
on the query and settings.
[The query-parallelism guide explains how blocks flow through it](https://clickhouse.com/docs/concepts/core-concepts/query-parallelism).

## Incremental materialized views

Partial aggregation can also move work from repeated queries into ingestion.
A dashboard that repeatedly requests daily purchase revenue can use partial
totals computed as events arrive, reducing the need to scan all raw events for
every request.

A ClickHouse **incremental materialized view** runs a query on each newly inserted
block and writes the result to a target table. It moves work into ingestion to
reduce work at query time.
[The materialized-view guide describes this tradeoff](https://clickhouse.com/docs/concepts/features/materialized-views/incremental-materialized-view).

The lab uses append-only data. Creating the view does not automatically process
rows already in the source table. Updating or deleting old source rows does not
automatically reverse their contributions to the target. Backfills, retries,
and corrections need an explicit design.

The target may hold several partial totals for the same day. The lab uses
`SummingMergeTree` and still queries the target with `sum(...) GROUP BY ...`.
That aggregation produces the answer without waiting for background merges to
finish.
[The target-engine documentation explains why that aggregation matters](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/summingmergetree).

## Shards and replicas

A **shard** holds a subset of the data. A **replica** holds a copy of a shard's
data. The partial-result aggregation described above can extend across machines:
a distributed analytical query requests partial results from the shards and
combines them. Counting every replica as an independent dataset would
count the same data more than once.
[The Distributed engine documents query routing and aggregation](https://clickhouse.com/docs/reference/engines/table-engines/special/distributed).

In a classic self-managed deployment, ReplicatedMergeTree coordinates through
ClickHouse Keeper or ZooKeeper. Replication is asynchronous, so a replica can lag
behind new writes and requires operational care.
[The replication reference describes that contract](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/replication).
ClickHouse Cloud uses a different architecture with SharedMergeTree and shared
object storage.
[The Cloud architecture has its own explanation](https://clickhouse.com/docs/products/cloud/features/infrastructure/shared-merge-tree).
The local lab uses one server without replication.

## Workload and operational tradeoffs

ClickHouse supports joins, updates, and deletes. I would investigate their cost
and semantics before using it as my application's transactional database.
[Update strategies](https://clickhouse.com/docs/concepts/features/operations/update/overview)
and [transaction support](https://clickhouse.com/docs/guides/developer/transactional)
have specific constraints and evolving options.

I would be cautious when most requests retrieve one mutable entity, correctness
depends on uniqueness or foreign-key enforcement, or the application requires
general multi-table transactions. An analytical deployment still requires
choosing types and sort keys, monitoring parts and merge capacity, and budgeting
memory for large joins or high-cardinality grouping. **High cardinality** means
many distinct values, which can make an aggregate's intermediate state large.

I would evaluate whether summarizing many events is enough of the workload to
justify those choices and operating costs.

## Run ClickHouse locally

The lab uses Docker with its Compose plugin and generates its own synthetic
data. The server is pinned to
[26.9.8.3](https://github.com/ClickHouse/ClickHouse/releases/tag/v26.9.8.3-stable),
the stable release used to verify these commands on October 1, 2026. The pin
makes the exercise reproducible; it does not identify the latest release at the
time of reading.

### Start a server

Create a directory and save the following configuration as `compose.yaml`.
It uses the [official ClickHouse Docker image](https://clickhouse.com/docs/get-started/setup/self-managed/docker),
stores data in a named volume, and binds HTTP to `127.0.0.1:8124` on your
computer. Use these credentials only for the local exercise.

```yaml
name: clickhouse-primer-lab

services:
  clickhouse:
    image: clickhouse/clickhouse-server:26.9.8.3
    environment:
      CLICKHOUSE_USER: practice
      CLICKHOUSE_PASSWORD: practice-local-only
      CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT: 1
    ports:
      - 127.0.0.1:8124:8123
    volumes:
      - clickhouse-data:/var/lib/clickhouse
    ulimits:
      nofile:
        soft: 262144
        hard: 262144
    healthcheck:
      test:
        - CMD-SHELL
        - >-
          clickhouse-client --user "$${CLICKHOUSE_USER}"
          --password "$${CLICKHOUSE_PASSWORD}" --query 'SELECT 1'
          >/dev/null 2>&1
      interval: 2s
      timeout: 5s
      retries: 60
      start_period: 20s

volumes:
  clickhouse-data:
```

Start Docker, then start the server and open its bundled SQL client:

```sh
docker compose up -d --wait --wait-timeout 180
docker compose exec clickhouse clickhouse-client \
  --user practice --password practice-local-only
```

### Generate a million events

Run the following statements at the client prompt. `numbers(1000000)` supplies
integers from 0 through 999,999. Each event is derived deterministically from
that number, producing an intentionally synthetic distribution.

```sql
SELECT version();
CREATE DATABASE lab;

CREATE TABLE lab.events
(
    event_id UInt64,
    event_time DateTime('UTC'),
    user_id UInt32,
    country LowCardinality(String),
    event_type LowCardinality(String),
    revenue_cents UInt64
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (country, event_time);

INSERT INTO lab.events
SELECT
    number AS event_id,
    toDateTime('2026-09-01 00:00:00', 'UTC')
        + toIntervalSecond(number % 2592000) AS event_time,
    toUInt32(number % 10000) AS user_id,
    ['DE', 'GB', 'US'][1 + number % 3] AS country,
    multiIf(number % 10 = 0, 'buy',
            number % 10 < 3, 'cart', 'view') AS event_type,
    if(number % 10 = 0, number % 9900 + 100, 0) AS revenue_cents
FROM numbers(1000000);
```

Country codes and event types repeat in this dataset, making them suitable
examples of `LowCardinality(String)` and its dictionary encoding. This does not
make it the appropriate type for every string.
[The type reference describes its intended use](https://clickhouse.com/docs/reference/data-types/lowcardinality).

The monthly partition groups data for lifecycle operations. Partitioning,
sorting rows within a part, and distributing data across machines are separate
mechanisms. All initial events fall in September, so this dataset does not
demonstrate pruning across several monthly partitions.

### Query and inspect the event data

```sql
SELECT count() AS events FROM lab.events;

SELECT
    country,
    count() AS events,
    countIf(event_type = 'buy') AS purchases,
    sum(revenue_cents) AS revenue_cents
FROM lab.events
GROUP BY country
ORDER BY country;
```

The count query returns 1,000,000. Grouping the events by country returns:

| country | events | purchases | revenue_cents |
| ------- | -----: | --------: | ------------: |
| DE      | 333334 |     33334 |     167817130 |
| GB      | 333333 |     33333 |     168150270 |
| US      | 333333 |     33333 |     168483600 |

Inspect index selection for a query restricted to one country and one day:

```sql
EXPLAIN indexes = 1
SELECT sum(revenue_cents)
FROM lab.events
WHERE country = 'US'
  AND event_time >= toDateTime('2026-09-02 00:00:00', 'UTC')
  AND event_time < toDateTime('2026-09-03 00:00:00', 'UTC')
SETTINGS use_query_condition_cache = 0,
         use_skip_indexes_on_data_read = 0;
```

In the verified run, `PrimaryKey` selected 5 of 123 granules. This describes the
plan for this dataset and version; it is not a timing benchmark. The settings
remove query-condition cache effects to make index selection easier to inspect.
They are not general performance recommendations.

Remove `EXPLAIN indexes = 1` and the `SETTINGS` clause to execute the query.
It returns 14,477,400 cents. Replace the sum with `count()` to count the 28,800
matching events. When comparing keys or filters, check both the ranges the plan
can skip and whether the query still returns the same answer.

Inspect the table's active storage parts:

```sql
SELECT partition, name, rows, marks
FROM system.parts
WHERE database = 'lab' AND table = 'events' AND active
ORDER BY name;
```

Background work can change part names and counts. `system.parts` exposes the
server's physical storage state; the application does not maintain it as another
table.

### Create an incremental materialized view

Create the target table and view **after** inserting the million rows:

```sql
CREATE TABLE lab.daily_events
(
    day Date,
    country LowCardinality(String),
    events UInt64,
    revenue_cents UInt64
)
ENGINE = SummingMergeTree
PARTITION BY toYYYYMM(day)
ORDER BY (country, day);

CREATE MATERIALIZED VIEW lab.daily_events_mv TO lab.daily_events AS
SELECT
    toDate(event_time) AS day,
    country,
    count() AS events,
    sum(revenue_cents) AS revenue_cents
FROM lab.events
GROUP BY country, day;

SELECT sum(events) FROM lab.daily_events;
```

The result is 0 because creating the view did not backfill existing events.
Insert another 100,000 events, continuing the IDs from the first batch:

```sql
INSERT INTO lab.events
SELECT
    number AS event_id,
    toDateTime('2026-09-01 00:00:00', 'UTC')
        + toIntervalSecond(number % 2592000) AS event_time,
    toUInt32(number % 10000) AS user_id,
    ['DE', 'GB', 'US'][1 + number % 3] AS country,
    multiIf(number % 10 = 0, 'buy',
            number % 10 < 3, 'cart', 'view') AS event_type,
    if(number % 10 = 0, number % 9900 + 100, 0) AS revenue_cents
FROM numbers(1000000, 100000);

SELECT count() FROM lab.events;
SELECT sum(events) FROM lab.daily_events;

SELECT day, country,
       sum(events) AS events,
       sum(revenue_cents) AS revenue_cents
FROM lab.daily_events
GROUP BY country, day
ORDER BY day, country;
```

The raw table contains 1,100,000 events, but the target accounts for only the
100,000 events in the second batch. Excluding the first million demonstrates
that the view processes new insertions. A production rollup would need a planned
backfill that avoids gaps or double counting while ingestion continues.

### Stop or remove the local server

Exit the SQL client with `exit`. To query over HTTP, run this command from
another terminal in the same directory:

```sh
curl --fail --user practice:practice-local-only \
  'http://127.0.0.1:8124/?query=SELECT%20count()%20FROM%20lab.events'
```

The command should print `1100000`. Stop the server and retain its data volume:

```sh
docker compose down
```

The volume preserves tables and rows across restarts. Rerunning the creation
and insert statements without checking that state can conflict with or add to
existing data. To stop the lab and **erase its saved data**, run:

```sh
docker compose down -v
```

The official [SQL playground](https://sql.clickhouse.com/) provides existing
datasets to query without installing a server. For a local alternative to
Docker, the [quick-install guide](https://clickhouse.com/docs/get-started/setup/self-managed/quick-install)
covers the native binary and `clickhouse local` for file-oriented experiments.

## Source code entry points

The tested release has three source-code entry points for the mechanisms in
this post:

- [ColumnVector.h](https://github.com/ClickHouse/ClickHouse/blob/v26.9.8.3-stable/src/Columns/ColumnVector.h):
  array-backed numeric columns and operations such as filtering.
- [MergeTreeDataSelectExecutor.h](https://github.com/ClickHouse/ClickHouse/blob/v26.9.8.3-stable/src/Storages/MergeTree/MergeTreeDataSelectExecutor.h):
  selecting parts, columns, and mark ranges for a read.
- [AggregateFunctionSum.h](https://github.com/ClickHouse/ClickHouse/blob/v26.9.8.3-stable/src/AggregateFunctions/AggregateFunctionSum.h):
  the implementation behind a familiar aggregate.

I would next query a real event dataset with two or three questions I need
answered. That would let me evaluate which data ClickHouse reads, how fresh the
results are, and what the ingestion pipeline costs to operate.
